## 一、结论先给：不是「一个项目里两个板块」，是「两个独立项目」

你的账号 `/user/project/list` 返回：

```json
[{"userId":10000001, "projectId":3356, "accountId":10000101},   ← 洗衣饮水吹风
 {"userId":10000001, "projectId":4000, "accountId":10000002}]    ← 洗浴
```

| | 洗浴板块 | 洗衣饮水吹风板块 |
|---|---|---|
| `projectId` | **4000** | **3356** |
| `accountId` | **10000002** | **10000101** |
| 项目名 | 某某大学洗浴 | 某某大学洗衣饮水吹风 |
| `tenantId` | 571 | 571（同一租户） |
| 余额 | **0.940 元**（独立钱包） | 26.140 元（独立钱包） |
| 账单里的设备 | `热水表` | `饮水机` / `吹风机` / `洗烘设备` |

**两个板块的账户、余额、账单完全是分开的。**同一个手机号下有两条独立账户。

> ⚠️ 这解释了一个我一直没注意的细节：两次抓包的 `accountId=10000101`、`projectId=3356`
> ——抓到的全是洗衣饮水吹风板块。**洗浴板块（linyu 主战场）从来没被抓过。**

## 二、那么 linyu 到底做的是哪个板块？

**做的是 4000（洗浴）。** 证据：

| 证据 | 说明 |
|---|---|
| 设备名 `热水器-…` / `热水表-…` | 4000 的账单里全是 `热水表:热水表-洗浴热水-3号宿舍楼-6层-601房` |
| `downRate/rateOrder` | 按用量计费，是热水表的模式 |
| `queryUsing` 有进行中订单 | 热水表长时间开着 |
| MQTT 推 `consumeMoney` 实时消费 | 按量计费才有实时金额 |
| 4000 的模块列表查不到 | `/project/module/list` 用 4000 查返回「**没有项目权限，请确认身份**」 |

最后这条很重要：**3356 有项目权限，4000 没有**（虽然账号绑定了 4000 的账户）。
说明 linyu 现有的 token 用法（`accountId=10000101` + `projectId=3356`）能玩转 3356，
但**要操作 4000 得用 `accountId=10000002` + `projectId=4000`**。

## 四、`lastOrder/byMac` 返回 null 的真正原因：时间窗口

实测三种情况：

| 查询 | 结果 |
|---|---|
| 3356 + 吹风机（1 小时前的单） | ✅ 有数据 |
| 3356 + 洗衣机（19 天前的单） | ❌ null |
| 4000 + 洗衣机 / 吹风机 | ❌ null（跨项目查不到，正常） |
| 3356 + 不存在的 MAC（`FFFFFFFFFFFF`） | ❌ null |

**洗衣机有 2 笔真实订单**（10-05 10:24:56 和 14:02:38，各 4.00 元），
都距今 19 天。吹风机最近一单是 1 小时前。

所以 `lastOrder/byMac` **只查最近一段时间的单**（具体窗口未知，介于 1 小时 ~ 19 天之间），
**不是设备维度的永久历史**。乱填 MAC 也返回同样的 null（不做错误区分）。

> 教训：不要用 `data == null` 去判断「设备没被用过」。

## 六、对开发方向的决定性影响

### 你要加的功能 = 3356 板块的第二个业务

linyu 现在只管 4000（洗浴）。你想加的洗衣/吹风属于 **3356**，
这是一个**平级的第二个项目**，不是 linyu 某个功能的分支。

### 三条必须处理的架构问题

**1️⃣ 双账户，不是双板块**

linyu 的 `PrefsHelper` 只存了一套凭证（`accountId=10000101`、`projectId=3356`——
注意：**它抓的其实是 3356 的 accountId，却用在了 4000 的项目上**？需要核实）。

这是个必须查清的点：linyu 登录后拿到的 `userAccount` 到底是哪个项目的。
如果用户用 linyu 洗澡正常，那它的 `accountId` 必然是对的（=10000002 那套）。

**2️⃣ 加洗衣/吹风必须切项目上下文**

不能简单加两个接口就完事。需要：
- 登录后调 `/user/project/list` 拿到所有绑定项目
- 进入洗衣/吹风板块时，把请求上下文的 `projectId`/`accountId` 切成 3356/10000101
- 钱包余额、账单也要跟着切（两个钱包是独立的）

**3️⃣ `/project/module/list` 是判断「这个学校有哪些业务」的正解**

比硬编码 `bigTypeId` 更可靠：`isUse=1` 的模块才显示图标。
你截图里那个 4×2 的图标网格，就是按这个接口渲染的。

### 建议的开发顺序

1. **先做只读的板块切换**：`/user/project/list` → 显示两个板块 → 点进去能看各自的设备/余额/账单
   （零成本、不需要新接口知识、能立刻验证双账户模型）
2. 再做 3356 板块的洗衣/吹风下单（这次抓包的数据已经够了）
3. 最后考虑要不要把 4000 的洗浴也纳入统一 UI

> ⚠️ 别急着写 `ModeOrderController`。**先把双项目模型理清楚**，
> 否则会写出「用 4000 的 accountId 去调 3356 的下单接口」这种必然失败的代码。

## 七、还缺的验证点

| # | 缺什么 | 状态 |
|---|---|---|
| 1 | linyu 登录后 `userAccount.projectId` 到底是 4000 还是 3356 | ✅ 已核实，见下 |

| 3 | `lastOrder/byMac` 的时间窗口具体多长 | ⚠️ 只能记录现象（介于 1 小时~19 天） |

### 第 1 条已核实：两个项目账户完全隔离

用同一个 `loginCode` 分别以两个项目上下文调 `/account/info`：

| 上下文 | 返回 projectId | 返回 accountId | userId |
|---|---|---|---|
| `projectId=3356&accountId=10000101` | 3356 | 10000101 | 10000001 |
| `projectId=4000&accountId=10000002` | 4000 | 10000002 | 10000001 |

**同一个 `loginCode`（= 同一个 userId）可以操作两个项目，但必须配对正确的 accountId。**
用错组合会拿不到数据（`/project/module/list` 用 4000 报「没有项目权限」）。

这意味着：

- `NetworkModule.updateAuth(loginCode, userId, accountId, projectId, telephone)`
  那 5 个参数**必须整体切换**，不能只换 projectId
- linyu 现在存的是哪一套？需要看它登录时怎么取 `userAccount`。
  如果它取的是 `data.userAccount`（登录响应里那个），那就是**单项目**写法，
  加第二板块时必须改成「先查 `/user/project/list`，再按板块挑 accountId」

### 第 2 条建议的取法

4000 的设备查询很可能还是 `/device/info/mac`（MAC 直查是全局的，实测用 4000
上下文查 3356 的 MAC 也能查到设备，返回里 `projectId` 仍是 3356）。
真正缺的是「洗浴板块的设备列表接口」——linyu 不一定需要它（它靠 BLE 扫描 + 扫码）。

## 八、一句话总结

- 你截图的两个板块 = **两个独立 projectId**（4000 洗浴 / 3356 洗衣饮水吹风），
  各自的 accountId、余额、账单完全隔离
- linyu 做的是 **4000（洗浴）**；你要加的洗衣/吹风在 **3356**
- 3356 内部再分 3 个 module（洗烘 / 饮水 / 吹风机），和截图二完全对应
- `lastOrder/byMac` 对洗衣机返回 null **不是板块问题**，是**时间窗口**问题
  （洗衣机最近一单在 19 天前，吹风机在 1 小时前）
- 所以加功能前**必须先做板块/账户切换**，否则会用错 accountId 写出必然失败的代码
