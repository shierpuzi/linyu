# 抓包过滤器 · 使用说明

给下一次抓包用的工具。**目标：把广告联盟、埋点、UDP 探测包滤掉，只留下趣智校园的业务请求。**

已用洗衣机抓包验证过，也用手造的「吹风机抓包」做过回归测试——换设备不会翻车。

---

## 一、下次抓完包，只要两条命令

```powershell
cd washer-probe

# 1) 过滤（把 zip 拖到命令行里，或者写路径）
python filter_capture.py ..\吹风机抓包.zip

# 2) 看结果
notepad filtered\report.md
```

报告会按这个顺序告诉你最要紧的事：

| 段落 | 看什么 |
|---|---|
| 💸 会被判定为「花钱」的调用 | **先看这个**。哪些请求是下单、扣了多少 |
| 余额轨迹 | 抓包前后余额差多少，验证「点一下扣几块」的硬证据 |
| 🔎 设备画像 | 吹风机的 `bigTypeId` / `smallTypeId`——写判定逻辑的唯一依据 |
| 🆕 本次新出现的接口 | 不在已知清单里的路径。**吹风机的新功能就藏在这里** |
| ⚠️ 靠内容嗅探救回来的会话 | 换了域名/端口但载荷带业务字段的，必须人工确认 |
| ⏱ 业务请求时序 | 完整调用顺序，照着写代码 |
| 📡 MQTT 推送 | 下单/洗完的推送内容 |
| 🗑 已过滤的噪音 | 被丢掉的东西和原因 |

## 二、抓包时的注意事项

### 抓包工具的过滤规则（省得又是一堆广告）

只留两个目标：

```
v3-api.china-qzxy.cn        ← 所有业务 HTTP
47.107.37.60:1883           ← MQTT 推送（下单成功/洗完通知在这里）
```

**第二个千万别漏。** 洗衣机的 `modeOrder` 响应是 `{"data": null}`，
下单成不成功、订单号是多少，**只能从 MQTT 推送里拿**。漏了它等于没抓到下单。

### 抓多长

| 设备 | 建议 | 理由 |
|---|---|---|
| 吹风机 | **完整一轮**（开 → 用 → 停/自动结束 → 进账单页） | 吹风机成本低、无噪音，是最适合抓全套的设备 |
| 洗衣机 | 单脱水（1 元 / 10 分钟） | 标准洗 35 分钟且晚上噪音大 |

**关键：抓到「结束」之后再等 60 秒。** 结算请求往往在结束后的几十秒内才发出来，
抓包提前关掉就前功尽弃。

### 建议顺手抓的四个场景

| # | 做什么 | 花钱 | 补什么缺口 |
|---|---|---|---|
| 1 | 设备**被占用**时打开详情页，停 10 秒 | 0 | `isUse` / 状态接口在占用态的返回 |
| 2 | **完整走一轮**，抓到底 | 少量 | 结束/结算流程长什么样 |
| 3 | 结束后刷新**账单页** | 0 | 这个设备在账单里的字段（不然 App 里会显示成热水器） |
| 4 | 如果 App 有「停止/取消」，点一次 | 少量 | 能不能中途停、退不退钱 |

第 1、3 项不花钱，先抓这两个也有价值。

## 三、脚本是怎么判断「业务 vs 噪音」的

不靠硬编码域名白名单——吹风机的接口路径必然和洗衣机不同，但域名不会变。

| 判据 | 说明 |
|---|---|
| 域名含 `qzxy` / `klcxkj` | 主判据。`v3-api` / `v4-api` / `oss` 都覆盖 |
| MQTT CONNECT 帧 | 二进制嗅探 `\x00\x04MQTT` |
| **内容嗅探**（兜底） | 载荷里有 `loginCode` / `deviceSnCode` / `orderNo` / `app_downRate` → 升级为业务会话并**告警** |
| 其余 | 归噪音，但**照样列在报告里**，不静默丢弃 |

> 内容嗅探是特意加的：万一服务端换了新网关（比如 `v4-api` 或者一个完全没见过的域名），
> 域名判据会失效。这时载荷里的业务字段会把它捞回来，并在报告顶部打 ⚠️。
> **看到那个 ⚠️ 一定要人工看一眼**——那意味着有新的服务端要研究。

## 四、产物

```
filtered/
├── report.md            ← 人读，看这个
├── sessions.json        ← 机器读，全部结构化数据
└── fixtures/http.json   ← 喂给 qzxy_washer.py 做离线回放
```

加 `--copy-sessions` 会把业务会话的原始文件也复制到 `filtered/raw/`（归档用）。

## 五、换设备要注意的地方

过滤器本身对设备无感知，但下面这两块是**洗衣机专用的**，吹风机要跟着改：

| 位置 | 现在 | 吹风机时怎么改 |
|---|---|---|
| `qzxy_washer.py` 的 `FIELD_ORDER` | 洗衣机 6 个接口的参数顺序 | 抓完看报告，按新接口的参数补进去 |
| `qzxy_washer.py` 的 `CHARGING_ENDPOINTS` | `modeOrder` | **把吹风机的下单接口加进去**，否则护栏漏掉 |

> `FIELD_ORDER` 里没登记的接口会直接 `KeyError` 报错——这是故意的，
> 宁可报错也不要拿错的参数去构造请求。

## 六、复跑验证

```powershell
python filter_capture.py ..\洗衣机消费抓包.zip   # 换回洗衣机抓包
python freeze_fixtures.py                        # 冻结两份 fixture（测试基准）
python test_filter.py                            # 过滤逻辑回归测试
python selftest.py                               # 报文逐字节比对（洗衣机+吹风机）
python qzxy_washer.py                            # 离线回放，一分钱不花
```

`test_filter.py` 里有 8 组用例，包括**真实吹风机抓包**和手动构造的假抓包
（新域名、新接口、新设备类型），专门验证**换了设备不会丢包**。改过滤器之后先跑它。

### ⚠️ fixtures 必须冻结

`filter_capture.py` 每次跑都会覆盖 `filtered/fixtures/http.json`——
也就是说跑过吹风机之后它就是吹风机数据了。
所以测试基准用 `freeze_fixtures.py` 生成的 `fixtures_washer.json` / `fixtures_dryer.json`，
不再依赖 `filtered/` 的当前状态。

## 附：两次抓包的分析结论

| 设备 | 报告 | 核心结论 |
|---|---|---|
| 洗衣机 | [抓包分析报告.md](抓包分析报告.md) | 142 会话→12 业务；`modeOrder` 一次扣 4 元全款 |
| 吹风机 | [吹风机分析报告.md](吹风机分析报告.md) | 101 会话→21 业务；**全程无停止接口，按套餐自动结束** |

两次的共同结论：

1. 下单接口都是 `POST /order/tcpDevice/downRate/modeOrder`，`xfModel=套餐modeId`
2. 都**一次预扣全款**，返回值都是 `data:null`，orderNo 只能从 MQTT 拿
3. 都**没有中途停止/退款接口** —— 不要做「停止」按钮
4. 金额字段单位混用：`modeMoney` 是厘，账单 `consumeMoney` 是元字符串

差异（必须按设备区分）：

| | 洗衣机 | 吹风机 |
|---|---|---|
| bigTypeId / smallTypeId | 6 / 3 | **7 / 5** |
| 套餐 | 4 档（1~5 元，10~45 分） | 3 档（0.6~2 元，3~10 分） |
| MQTT broker | 47.107.37.60 | **39.108.147.136** |
| `lastOrder/byMac` | 没调 | 调了（结束后的兜底） |
