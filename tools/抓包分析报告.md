**这笔账已经实锤了：`modeOrder` 是一次性预扣套餐全款、立即扣、下单那一刻就扣。**
`16.680 → 12.680`，差的 4.00 元就是 `modeMoney=4000` 厘。

### 和热水器的对比（决定了不能复用现有代码）

| | 热水器（linyu 已实现） | 洗衣机（抓包得到的） |
|---|---|---|
| 下单 | `downRate/rateOrder`（xfModel=0） | `downRate/modeOrder`（**xfModel=套餐 modeId**） |
| 计费 | 按用量，先预扣后结算 | **按套餐一次性预扣全款** |
| 停止 | `closeOrder` + `orderNo` | 抓包里**没有**停止/退款接口 |
| 状态 | `query/rateOrder/using` 返回 orderNo/state | `tcpDevice/washer/status`，空闲时 `data:null` |
| 剩余时间 | `autoDisConTime` | 只能靠 `modeTimeMinute` 自己算 |
| 下单确认 | `query/downRateResult` 会给 orderNo | **只靠 MQTT 推送**，HTTP 响应是 null |

> 关键差异：linyu 现在整套 `ShowerController` + `ShowerWatchService` + `SettlementEngine`
> 都建立在「`queryUsing` 是可靠状态源」这个前提上（`ShowerController.kt:214`、
> `ShowerWatchService` 的轮询）。**洗衣机上这个前提不成立**——`queryUsing` 对洗衣机没意义，
> `washer/status` 捕捉到的又是 null。硬塞进现有状态机会出现「首轮就判成订单没了→立刻结算」，
> 和老代码注释里记录过的坑一模一样。

## 三、回答你的问题：请求**够复现下单，不够做完整功能**

### ✅ 已经够的（可以写代码）

1. 设备识别：`bigTypeId=6` + `smallTypeId=3`，`snCode == macAddress 去掉冒号`（扫码绑定直接能命中）
2. 套餐列表与价格：`/device/mode/list?smallTypeId=3`，厘换算
3. 下单请求的**完整、可复现报文**（含参数顺序）
4. 下单成功的判据：MQTT `app_downRate_{phone}` 里的 `orderNo`
5. 扣款金额的验证方式：`/account/wallet` 前后差值
6. 认证方式：和热水器完全一样（loginCode + 双 telephone），linyu 的 `NetworkModule` 直接可用

### ❌ 不够的（4 个硬缺口）

| # | 缺什么 | 为什么必须 |
|---|---|---|
| 1 | **洗完/结算流程一次都没抓到** | 抓包在 10:25:12 就结束了，而标准洗要 **35 分钟**。`/order/consumeOrder/result/query` 对洗衣机灵不灵、还要不要查、怎么查，**完全没数据**。这让「显示本次洗衣消费」无法验证 |
| 2 | **`washer/status` 在「有订单时」返回什么不知道** | 唯一一次调用是空闲态（`data:null`）。如果运动中它也不给剩余时间/状态，那 UI 上「还剩 X 分钟」只能本地倒计时，且**无法发现洗衣机提前结束或故障** |
| 3 | **能不能中途停？停/取消了退不退钱？** | `smallType/id` 里 `isAllowClose=null` 是「不知道」不是「不能」。热水器那套「停止→结算」在洗衣机上可能压根不存在。**不搞清楚就写停止按钮，等于给用户一个不退款按钮** |
| 4 | **洗衣机在账单里长什么样** | `/order/query/account/bill/list` 一次都没抓。linyu 账单页靠 `description`/`bigTypeId` 上色和写文案，洗衣机可能显示成「热水器 🚿」或者压根不出现 |

### 次要缺口

- `modeOrder` 的**失败**长什么样（余额不足 / 洗衣机被占用 / 离线）——没有样本，错误码文案只能瞎猜
- 一台**被占用中**的洗衣机：`device/info/mac` 的 `isUse` 是不是会变成占用标记（抓包里空闲时是 `isUse:1`，语义反直觉），以及 `washer/status` 此时返回什么
- 只覆盖了 1 台设备 / 1 所学校（projectId=3356）、1 份 39 秒的样本

### 关于「不能扣我的钱」——代码层面的护栏

抓包已经证明 `modeOrder` 一发出就立刻扣全款、且**没有抓到任何退款接口**。所以：

1. **绝不做静默下单**。热水器那套「点一下就开始」的交互在洗衣机上必须改成
   「选套餐 → 显示『将扣 ¥4.00 / 35 分钟』→ 再点确认」。这是钱，不是水。
2. **开发期永不调用 `modeOrder`**。`washer-probe/qzxy_washer.py` 已经这么做了：
   离线模式下 `ChargeBlocked` 直接拦住（`selftest.py` 第 2 组用例就在验证这条护栏），
   联网还要同时给 `--live` **和** `--allow-charge` 才放行；只读模式给 `--live --read-only`。
3. **先做只读功能**：查看附近洗衣机、四种套餐与价格、占用状态、上次洗衣消费。
   这部分**一分钱不花**，可以完全靠本报告的抓包验证。
4. 真要跑通一次端到端，用 **单脱水 1 元 / 10 分钟**，别用 4 元标准洗。

## 七、一句话总结

抓包**足以复现洗衣机的下单请求**（已逐字节验证，含 4 元扣款实锤），
但**不足以支撑一个完整功能**——缺洗完/结算、缺运行中状态、缺能否中途停、
缺账单呈现四块。**不用开 root**，用同样的抓包工具、把过滤设成只留
`v3-api.china-qzxy.cn` + MQTT，花 1 元抓一次「单脱水」的完整 10 分钟就够了。
