## 三、最重要的三个结论

### 1️⃣ 全程没有任何「停止 / 取消 / 退款」接口

抓包 3 分 18 秒，包括完整一轮，**一个 stop/close/cancel/refund/shutdown 都没有**
（已用回归测试断言这条）。

结合数据：下单 00:12:24 → 钱包扣款 00:12:25 → 结束 00:15:25，**181 秒 ≈ 套餐 180 秒**。

**结论：吹风机（和洗衣机）是「按套餐预扣全款 + 服务端到点自动关停」，没有中途停这个功能。**
所以：
- linyu 那套 `closeOrder`（关阀）**完全不适用**
- **不要给吹风机做「停止」按钮**——点了没用，而且会让用户以为能退钱
- UI 上应该写「到点自动结束」而不是「停止使用」

> 这条对洗衣机同样成立。上一轮我猜「`isAllowClose=null` 是不知道」，
> 现在有实证了：**就是没有中途停**。

### 2️⃣ 下单成功只能靠 MQTT，HTTP 响应恒为 `null`

`modeOrder` 返回 `{"success":true,"data":null}`，**订单号不在里面**。
唯一来源是 MQTT 推送 `app_downRate_{phone}` 里的 `orderNo`。

**但开发期不必真的花钱** —— `lastOrder/byMac` 这个 GET 接口免费就返回了完整订单
（orderNo / modeName / 金额 / 设备），见下节。这是本轮最大的发现。

### 3️⃣ MQTT 服务器换了，而且不是 47.107.37.60

| 抓包 | broker |
|---|---|
| 洗衣机（10-05） | `47.107.37.60:1883` |
| 吹风机（10-24） | **`39.108.147.136:1883`** |

linyu 的 `utils/MqttManager.kt:13` 硬编码了 `tcp://47.107.37.60:1883`。

**别以为只有一台 broker。**两种可能：按学校/项目分片，或者旧地址已下线。
不管哪种，拿现有地址去连吹风机大概率一条推送都收不到，
**而订单号全靠它**——这会让新功能「看起来下单成功了但拿不到订单号」。

> 建议：连之前先确认。如果连不上，走 `lastOrder/byMac` 兜底拿 orderNo
> （这也正是官方 App 在结束后的做法）。

## 四、意外收获：两个不花钱就能用的接口

### `GET /order/query/lastOrder/byMac` — 最近一单（★ 开发期神器）

```
GET /order/query/lastOrder/byMac
    ?accountId=10000101&macAddress=C4%3A7F%3A0E%3A23%3A51%3ABE
    &telPhone=...&phoneSystem=android&loginCode=...&telephone=...
    &isHaier=0&projectId=3356&userId=10000001&version=6.5.29
```

返回：`orderId / orderNo / xfModel / modeName / modeMoney / modeTime / preDeductMoney /
consumeDate / deviceId / deviceName / macAddress / smallTypeId`

**零成本价值**：只要账号历史上用过这台设备，就能免费拿到真实的 orderNo 和套餐信息，
不用再花一分钱就能把「解析 MQTT / 显示套餐名 / 显示金额」全部验证完。
新设备类型接入时先调这个，能省掉反复花钱试错。

> **实测补充（2026-10-24 00:38 在线验证）**：
> - 吹风机 → 有历史单，返回完整订单
> - 洗衣机 → `data: null`（该账号没在这台洗衣机上留下可查的单）
>
> 结论：**这个接口按设备维度查，没有历史单就返回 null，不能当「设备空闲」的判据。**

### `GET /order/query/account/bill/list` — 月度账单（★ 类型判定的答案在这里）

两次抓包都**没抓到**这个接口（官方 App 账单页走 H5 + `bill/detail`）。
这次在线调用补上了：`data` 是账单数组（10 月 32 条、9 月 23 条），每条形如：

```json
{"billType": 2, "consumeBillDTO": {
  "orderId": "11868418", "orderNo": "13202610240012244626",
  "dealDate": "2026-10-24 00:12:24", "consumeDate": "...", "uploadDate": "...",
  "preDeductMoney": "0.6", "consumeMoney": "0.6",
  "description": "吹风机:吹风机-3号宿舍楼-6层-东边卫生间-1",
  "consumeType": "吹风机",        ← ★ 服务端直接给了中文类型名
  "consumeSceneType": 0, "deviceId": 1252, "runStatus": 1,
  "tradeSettlement": 1, "canComplain": 1, ...
}}
```

**关键发现：`consumeType` 直接是设备类型中文名。** 本月实测取值：

| `consumeType` | `consumeSceneType` | description 前缀 | 条数 |
|---|---|---|---|
| `饮水机` | 2 | `饮水机:` | 16 |
| `饮水机` | 0 | `饮水机:` | 9 |
| `吹风机` | 2 | `吹风机:` | 4 |
| `洗烘设备` | 0 | `洗烘设备:洗衣机-…` | 2 |
| `吹风机` | 0 | `吹风机:` | 1 |

⚠️ **`consumeType` 用的是大类名**：洗衣机显示 `洗烘设备`（不是「洗衣机」），
和 `/device/info/mac` 里的 `bigTypeName`（「洗衣机」）**不一致**。所以：

- linyu 现有的账单类型推导（`LoginModels.kt:107` 靠 `description` 前缀猜）
  可以改用 `consumeType`，比字符串前缀可靠
- 但**设备类型判据仍统一用 `bigTypeId` / `smallTypeId` 数字**，
  账单侧的名字只用于展示，别拿来做分支

### `GET /order/query/account/bill/detail` — 账单详情（已有接口，字段值得抄）

linyu 里已有 `getBillDetail`（`QzxyService.kt:87`），但**参数和用法值得注意**：

```

consumeDate=2026-10-24+00:12:24
```

返回字段（吹风机的实际值）：

| 字段 | 值 | 说明 |

| `deviceDescription` | `吹风机:吹风机-3号宿舍楼-6层-东边卫生间-1` | 账单页文案 |
| `modeInfo` | `电吹风模式一(3分钟)/0.6元` | **套餐信息直接给好了，不用自己拼** |
| `consumeMoney` | `"0.6"` | **元字符串**（不是厘！） |

### 另：H5 账单页无关紧要

`https://app-cold-water.china-qzxy.cn/billDetail` 是 WebView 加载的页面（`x-requested-with:
com.klcxkj.zqxy`，`accept: text/html`），**响应体是空的**（没抓到渲染后的 DOM）。
它只是壳，数据来自 `bill/detail` 接口。**不用管它。**

## 五、顺手修掉的一个真 bug（过滤器）

第一轮洗衣机抓包没暴露、这次吹风机暴露的问题：

**抓包工具会把多个 MQTT 帧塞进同一个 `.bin`。**吹风机的 `85/4.bin` 是

```
SUBACK (5 字节) + PUBLISH (582 字节)  ← 粘在一起
```

原来的 `decode_mqtt` 每个 `.bin` 只读第一个帧头，于是把 SUBACK 当全部、
**整条下单推送被吞掉**。报告里表现成「订阅成功但没收到推送」，看起来像服务端没推。

### MQTT broker 告警也加了

现在报告会检查 broker 是否等于 linyu 里硬编码的 `47.107.37.60`，不一致就告警（本次已触发）。

已加回归用例，位于 `test_filter.py` 的「0) 真实吹风机抓包」，
断言 `len(m["publishes"]) == 1`——这条断言就是为了防止解码器退化回「一个 bin 一个帧」。

### ⚠️ 还差的（都不影响开工）

1. **`washer/status` 在「使用中」返回什么** —— 抓包里只在空闲态调过一次（`data:null`），
   使用中没有调用。但既然 App 全程不轮询，这条**大概率不重要**
2. **`isUse` 的语义** —— 空闲时是 `1`，反直觉。可能是「是否可用」而非「是否在使用中」。
   被占用时返回什么没抓到（**下一个不花钱就能补的场景**：设备被占用时打开详情页）
3. **洗衣机是否也调 `lastOrder/byMac`** —— 上一轮洗衣机抓包**没调**这个接口
   （可能因为流程不同，或版本 6.5.28 → 6.5.29 新增）。建议对洗衣机也验证一下
4. **错误分支** —— 余额不足、设备离线、被占用时的错误码都没样本（只能照热水器的经验猜）

## 七、下一步建议

**不用再花钱抓包了。**剩下能免费补的只有一条：

> 找一台**正在被占用**的吹风机/洗衣机，打开详情页停 10 秒，看 `isUse` 和
> `washer/status` 返回什么。零成本，补掉上面第 1、2 条缺口。

然后就可以动手写代码了。架构建议（和洗衣机那轮结论一致，但现在证据更足）：

### 复用（都现成）

- `api/NetworkModule.kt` — 认证 + `Config-Project/Config-Keys` 头
- `api/SafeApi.kt` 的 `parse()` / `awaitString()`
- `model/DeviceModels.kt` 的 `DeviceInfo`
- `utils/MoneyFormat.kt:27` `milliToYuan()` — **厘换算**
- `QzxyService.getBillDetail` — 已有，账单详情能直接用

### 新写（别改老代码）

- `data/ModeOrderController.kt` — 洗衣机 + 吹风机**共用**这条通道
  （两者下单接口、套餐接口、结算接口**完全相同**，只有 `smallTypeId` 和套餐档位不同）
- 状态源用 `lastOrder/byMac`，**不要**接 `ShowerWatchService` 的 `queryUsing` 轮询
- 倒计时按 `modeTimeQuantity`（秒）本地算

### 关键：倒计时必须本地算 + 允许「结束时间过了但没收到任何通知」

抓包证明 App 在 180 秒里**零请求**。这意味着：
- 服务端不会通知你「结束了」（至少 6.5.29 的 App 没等这个通知）
- 如果本地倒计时结束就以为结束，但服务端其实算错了时间，就会不一致
- **稳妥做法**：倒计时到 0 后，调一次 `lastOrder/byMac` 确认订单存在且时间对得上，
  再显示「本次消费 0.6 元」。这条比热水器那套轮询便宜得多（一次就够）

### UI 上必须做对的

- **不给停止按钮**（没有这个功能）
- 套餐选择页显示「0.6 元 / 3 分钟」，点了要先确认再下单（**一发出就扣全款**）
- 结束文案写「到点自动结束」，不写「已停止」
