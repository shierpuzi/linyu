## 一、项目是什么

`linyu/` — 趣智校园第三方 Android 客户端（Kotlin + Jetpack Compose，包名 `com.hualala.linyu`）。
原本只做**洗浴（热水表）**，本次开发扩展到**洗衣 / 吹风机（按套餐计费）**。

工具目录 `washer-probe/` 是抓包分析与在线验证脚本，**不属于 app 代码**。

## 二、30 秒理解业务模型（最关键的一段）

### 学校有两个**独立项目**，不是两个板块

| 板块 | projectId | accountId | 业务 | 计费方式 |
|---|---|---|---|---|
| 洗浴 | **4000** | **10000002** | 热水表 | 按量计费，可中途关阀 |
| 洗衣饮水吹风 | **3356** | **10000101** | 洗烘 / 饮水 / 吹风机 | **按套餐一次性扣全款** |

- 两个钱包独立、账单独立、设备独立
- `loginCode` 是**全局一套**（一个 userId 一个）
- **`projectId` 和 `accountId` 必须成对切换**，只换 projectId 会报「没有项目权限」

> 实测证据见 `washer-probe/板块与项目核实.md`

### 两种计费通道完全不同，不要混

**分流依据是「计费模型」，不是设备类型**（`ModeOrderPolicy.billingModel`，有单测）：

| | 按量计费 `METERED` | 套餐计费 `PACKAGE` |
|---|---|---|
| 哪些设备 | 热水器 / 洗手台 / **饮水机** | 洗衣机（big6）/ 吹风机（big7） |
| 下单 | `downRate/rateOrder` | `downRate/modeOrder`（`xfModel`=套餐 modeId） |
| 扣费 | 先预扣、按量结算 | **一次性扣全款，不可退** |
| 停止 | `closeOrder` 可以停 | **没有任何停止/取消/退款接口** |
| 状态 | `query/rateOrder/using` 可靠 | `washer/status`，空闲 `data:null`；占用态**无样本** |
| orderNo | `downRateResult` 给 | 只能 MQTT 或 `lastOrder/byMac` / `bill/detail` |
| 结束 | 用户主动 | **服务端到点自动关停** |
| 界面 | `ShowerScreen`（已用时长 + 结束按钮） | `ModeOrderScreen`（选套餐 + 剩余倒计时 + 无停止） |

> ⚠️ **饮水机在洗衣饮水吹风项目里，但计费是按量**。
> 账单实测：饮水机 `preDeduct=2.0` 而 `consumeMoney=0.1/0.44`（不等）；
> 洗衣/吹风是 `preDeduct == consumeMoney`（相等）。
> 用户明确说饮水机这次不做，走原有功能。

### 点开设备后去哪（2026-10-24 #19 / #20）

**三条入口统一走 `MainViewModel.routeAfterDeviceInfo()`**（首页卡片 / 扫码 / 收藏项）。
不要在各入口各写一遍「弹详情」——漏一处就出现"有的入口跳过了有的没跳过"。

| 计费模型 | 去哪 | 理由 |
|---|---|---|
| `PACKAGE`（洗衣机 / 吹风机） | **直接进选套餐页**（`ModeOrderScreen`） | 选套餐不扣钱，多点一次纯浪费 |
| `METERED`（热水器 / 洗手台 / 饮水机） | **直接进全屏操作页**（`MeteredDeviceScreen`） | 比小弹窗好看，但「开始使用」仍需二次确认 |

> ⚠️ **按量计费设备的「开始使用」不能直接开阀**：`requestStartMetered()` 只弹确认框，
> 用户点确认后才调 `confirmStartMetered()` → `startShower()`。
> 开阀是**立刻出水并计费**的动作，误触就是钱和水。
>
> **套餐下单同理**：`confirmModeOrder()` 只做校验 + 弹 `ConfirmStartDialog`，
> `commitModeOrder()` 才真正发 `modeOrder`。两者都有单测/注释锁着，别合并成一步。

### 收藏设备（#20）

**和「上次使用」是两回事**：

| | 上次使用（`PrefsHelper.lastDevice*`） | 收藏（`data/FavoriteStore.kt`） |
|---|---|---|
| 数量 | 1 条，每次操作被覆盖 | 多条，上限 30 |
| 写入 | 自动 | **用户主动**（长按 / 心形按钮） |
| 需要联网 | 是（回查台账） | **否**（字段全落盘） |
| 杀后台 | 可能丢 | 保留 |

**入口**
- 附近设备列表**长按**卡片 → 收藏/取消（先查台账补全字段，附近设备只有 MAC/名字）
- 使用页**右上角心形** → `toggleFavoriteCurrent()`，**两种计费页都有**
- 首页「收藏设备」区块 → 点击直接进对应操作页

**⚠️ 收藏必须存 `bigTypeId`/`smallTypeId`**：离线时要靠它判断计费模型来分流。
只存 MAC 再回查是错的——离线会退化成一行 MAC，而且无法分流。

### 「上次使用」也走新流程（#21）

**原来那张卡片右下角是「开始」按钮，点一下直接 `openValve`** ——按量计费设备
立刻出水并计费，而它在首页列表里，滑动时误触就出水。

现在：**去掉按钮，整卡可点**，走 `openLastDevice()`：
- **有活跃订单** → 恢复使用页（不重新开阀、不重复扣费）
- 否则 → `routeAfterDeviceInfo()`，和其他入口同一条路

### 页面滑移动效（#21）

`MainScreen` 用 `AnimatedContent` 包住「列表 ⇄ 设备页」，参数**照抄 `MainActivity`
的 tab 切换**（`dampingRatio=0.78f, stiffness=420f` + spring 淡入淡出）：

- 进入设备：新页从右滑入（`initialOffsetX = +full`）
- 返回：反向

> ⚠️ **主页分支必须内联**在 `AnimatedContent` 的 lambda 里，不能抽成独立函数——
> 它引用 `scanLauncher` / `context` / `filteredDevices` / `hasScanPerm` 等十几个局部变量，
> 抽出去要传一堆参数（试过一次，编译报 12 个 Unresolved）。

### 待确认页防抢占（#21 / #22）

用户停在选套餐页/确认弹窗/按量计费页犹豫时，设备可能被别人抢。
`startPreemptWatch(sn, packageBilling)` 每秒查一次，**两种模型查不同接口**：

| 计费模型 | 接口 | 占用判据 |
|---|---|---|
| 套餐（洗衣机/吹风机） | `washer/status` | `errorCode==307` 或 `success && data != null` |
| 按量（热水器/洗手台/饮水机） | `query/rateOrder/using` | `errorCode==307` 或 `success && orderNo != null` |

⚠️ **两者判据不能混用**：按量设备的 `data` **永远非空**（带 orderNo/isOwner），
空闲时只是 `orderNo == null`。照搬套餐的 `data != null` 会让热水器**永远显示被占用**。
`PreemptBothBillingTest` 锁着这条。

| 查到的状态 | 处理 |
|---|---|
| `Busy` | 页面顶部横幅「设备正在被使用 + 剩余时间」，**按钮禁用** |
| 空闲 | 清除提示，允许操作 |
| 请求失败 | **不算被抢**（断网时判"被抢"会让用户明明能用却被禁用） |

**只降级不打断**：不自动关弹窗、不自动跳页——用户能看到"为什么不能点了"。

生命周期：进页面（`openMeteredScreen` / `enterModeOrderPicker` / 确认弹窗）启动；
开阀成功 / 下单成功 / 关页面停止。

### 🎯 占用态样本（已采到，别再写「无样本」）

**2026-10-24 09:51 轮询抓到的第一个 `washer/status` 占用态响应**：

```json
{"success":true,"errorCode":307,"errorMessage":"设备正在使用中",
 "data":{"expireTimes":729,"orderNo":null,"isOwner":false,"accountId":null, ...其余全 null}}
```

| 事实 | 说明 |
|---|---|
| `success` **仍是 true** | 只看 success 会误判；必须看 `errorCode == 307` |
| `data` 非空但 `orderNo` 是 **null** | 别人的单不给单号，**别指望从这里取 orderNo** |
| **`expireTimes` 是剩余秒数** | 实测 729 → 649 → 589 递减，间隔 80s/60s 与轮询节奏吻合 |
| `isOwner` | 别人占用时 `false`；自己的单未采样（推测 true） |

**交叉验证**：同期 `lastOrder/byMac` 那单是「快速洗 25 分钟」、09:38:39 下单。
`09:38:39 + 25min = 10:03:39`；而 `09:51:32` 的 `expireTimes=729s` → `10:03:41`。
**吻合到 2 秒**，两个接口数据一致。

完整样本（含三轮递减表）→ `washer-probe/samples/占用态样本-20261024.md`

**代码判据**（`ModeOrderController.queryStatus()`）：
```kotlin
resp.errorCode == ERROR_IN_USE(307) -> Busy(busyReason(data))
resp.success -> Busy(busyReason(data))
else -> Unknown(...)      // 真失败才 Unknown
```

### ✅ 已解决：倒计时三个 bug（2026-10-24 #14）

| 现象 | 根因 | 修法 |
|---|---|---|
| 倒计时**变负数不消失** | `setOngoing(true)` 系统永不自动撤；`Chronometer` 过了 `when` 继续往下数 | `setTimeoutAfter(剩余+60s)`，交给系统计时 |
| **胶囊 3:00 不倒数** | `shortCriticalText` 发通知时写死，要更新只能重发 | `startModeOrderAutoRefresh()` Handler 每 30 秒重发 |
| 通知**一直挂着** | 撤通知靠 `viewModelScope` ticker，App 退后台就停 | 同上 + 启动时 `cancelStaleModeOrder()` 兜底 |

**实测证据**（完整记录见 `washer-probe/倒计时修复实测.md`）：
```
flags=ONGOING_EVENT|ONLY_ALERT_ONCE|PROMOTED_ONGOING   ← 流体云提升生效
timeout=PT3M29S → PT2M29S                             ← 每 30 秒重发已生效
android.requestPromotedOngoing=Boolean (true)
android.shortCriticalText=String [length=5]
到点 10:16:55 + 60s → 10:17:55 自动消失 ✅
```

> **重要**：`PROMOTED_ONGOING` 出现了，说明 ColorOS **认** `android.requestPromotedOngoing`
> 这套 extras。之前「胶囊 3:00 不动」纯粹是因为没人重发，不是 ROM 不认。

## 七、绝对不要做的事

1. **不要给洗衣/吹风做「停止」按钮** —— 服务端没有这个接口，点了没用还会让用户以为能退款
2. **不要用 `mergedBills` 做业务判断** —— 跨板块 orderNo 可能撞号，关阀/结算/对账必须用当前板块的 `billHistory`
3. **不要把套餐设备接进 `ShowerWatchService`** —— 它的 `queryUsing` 轮询对套餐设备是错误的信号源，会导致"首轮就判订单没了"
4. **不要用设备名判断类型** —— 只用 `bigTypeId` / `smallTypeId` 数字（洗衣机在账单里叫「洗烘设备」、台账里叫「洗衣机」，两个名字）
5. **不要用 `smallTypeId` 覆盖 `bigTypeId`** —— 历史上 `smallTypeId=1` 被误当蓝牙特征，导致全校设备开不了阀
6. **不要自己写金额换算** —— 用 `MoneyFormat.milliToYuan()`。注意：`modeMoney` 是**厘**，账单 `consumeMoney` 是**元字符串**，差 1000 倍
7. **不要用 `isUse` 判断「是否在用」** —— 空闲时它也是 `1`
8. **不要用 `lastOrder/byMac` 返回 null 判断「没用过」** —— 它有 1 小时左右的时间窗口
9. **不要把饮水机并进套餐通道** —— 它在同一项目里但按量计费，必须走 `ShowerScreen`。
   判据用 `billingModel`，不要看设备名或项目 id
10. **套餐下单拿不到 orderNo 时不能报失败** —— 钱可能已扣，报失败会让用户重试扣第二份。
    必须显示「网络状态不佳，请刷新核对」（`PlaceOrderResult.AwaitingOrderNo` 就是这个语义）
11. **不要让按量计费设备跳过详情框** —— 热水器/饮水机点开即开阀，会立刻出水计费。
    只有 `billingModel == PACKAGE` 才允许直达（`SkipDetailPolicyTest` 锁着这条）
12. **不要把 `MainScreen.kt` 里的组件当成可删的装饰** —— `ProjectSwitcher` 曾被误删过一次，
    编译器不报、测试全绿（UI 没单测），表现只是「板块切换入口消失」。
    改完这个文件必须过一遍下面的自检清单。
13. **不要在`每个入口`上重复补同一段逻辑** —— #28 修「设备页余额取错板块」时，
    把 `loadDeviceBoardWallet()` 只加在 `openMeteredScreen()` 上，结果「收藏」那条路
    没修到，用户直接报「修 bug 修一半」（#29）。
    **正确做法**：`grep 'selectedDevice ='` 把所有赋值点列一遍，或者收口到
    `selectedDevice` 的 setter / 共享函数里改一次。同理适用于任何「多入口同一逻辑」。
14. **不要**把「设备页显示的余额」和「当前板块的钱包」混为一谈 —— 见第十节。
    设备页必须用 `DeviceInfo.projectId`，不是 `currentProjectId`。

### 「通知不显示」的排查顺序（已踩过）

1. **权限**：`dumpsys package <pkg> | Select-String POST_NOTIFICATIONS` → 要 `granted=true`
2. **渠道是否存在**：`dumpsys notification | Select-String "mId='linyu_"` 
   ⚠️ **渠道只在首次调 `ensureChannels` 时创建**，装完不打开 App 是看不到的
3. **是否被系统拦**：找 `intercepted: ...|<pkg>|1006|...` —— 有这行说明**发出了但被拦**
4. **勿扰状态**：`settings get global zen_mode`（1 = 开启）
   + `dumpsys notification | Select-String "ZenRule"` 看规则时段
5. **渠道是否穿透勿扰**：看该渠道的 `mBypassDnd`
6. **统计**：`numEnqueuedByApp` / `numPostedByApp` / `numBlocked` 三者对比

> 实测结论：本机开了「睡眠勿扰 23:30~05:00」，`zen_mode=1`，
> 老渠道 `mBypassDnd=false` → 套餐倒计时通知全被吞。
>
> **⚠️ 这条结论后来被修正了两次，最终状态见下面「ColorOS 倒计时」一节。**
> 简版：① `setBypassDnd(true)` 需要 `ACCESS_NOTIFICATION_POLICY` 特殊权限，
> 没权限时被静默忽略；② 用户最终选了「不主动穿透勿扰」；
> ③ **真正让通知出不来的根因是渠道懒加载**（见开发日志 #9）。

## 十、登录凭证怎么来

- `loginCode` 是单点的：任何一处登录，其余立即失效
- 官方 App / 原版 linyu / dev 包三者会互相挤
- dev 包通过 `local.properties` 预置凭证（`QZXY_PREFILL_*`），启动即登录
- **公开构建（store flavor）永远是空串**，`verify_apk.py` 会验证这一点
- **测试 loginCode 登录时要清空预置凭证**，否则启动就自动登录、根本看不到登录页：
  打包前把 `local.properties` 里 5 个 `QZXY_PREFILL_*` 值置空，打完记得恢复

### 三种登录方式（2026-10-24 起）

| 方式 | 接口 | 需要的输入 |
|---|---|---|
| 密码登录 | `POST /user/login` | 手机号 + 密码（MD5 取后 10 位大写） |
| 验证码登录（默认） | `POST /user/registerAndLogin` | 手机号 + 短信验证码，**未注册自动建号** |
| **loginCode 登录** | 无（直接复用已有会话） | **loginCode + userId** |

### ⚠️ loginCode 登录必须两个字段（实测，别试着重构掉）

服务端把 `loginCode` 和 `userId` 当作**一对**来识别会话。2026-10-24 逐接口实测：

| 请求 | 结果 |
|---|---|
| 只有 `loginCode` | `errorCode=8 未获取到用户信息` ❌（6 个接口全如此） |
| `loginCode` + `accountId` / `+ projectId` / `userId=0` | 全部 `8` ❌ |
| **`loginCode` + `userId`** | ✅ `/user/project/list` 返回两条板块 |

`loginCode` 是 32 位随机 hex，**反推不出 `userId`**，所以只能让用户一起粘。
拿到这两个之后，其余认证参数由 `AuthRepository.loginWithCode()` 自动解析：

```
loginCode + userId
  → GET /user/project/list      → accountId + projectId（同时验证 loginCode 有效）
  → GET /account/info           → telephone / name / 学号
```

**教程**（告诉用户怎么抓）：
<https://github.com/shierpuzi/linyu/blob/master/docs/WIKI-抓包获取loginCode.md>

App 已登录时**从任意业务请求的 URL 里**就能抠出全套参数，不用重新登录、
不会挤掉正在用的 App。所以登录页的输入框允许**粘整条 URL**
（`LoginCodePolicy.extractLoginCode` 自己找 32 位 hex）。

### `projectId` 的两个用途（别搞混）

| 场景 | 该用哪个 |
|---|---|
| 板块列表 / 切换 | **当前板块**（`currentProjectId`，认证参数里那个） |
| 设备页显示余额 | **设备自己所属板块**（`DeviceInfo.projectId`，见 #28） |

⚠️ 设备页用错就是「洗浴页显示洗衣板块的钱」——这是 #28/#29 修了两轮的 bug。
判定逻辑收口在 `data/DeviceBoardPolicy`，**不要在界面里自己判断**。
