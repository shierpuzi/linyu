## 关键设计（都有代码注释，这里只列要点）

### 钱相关（最重要）

1. **`placeOrder` 先落盘再发请求** —— 崩在请求途中也知道「可能已扣钱」
2. **请求抛异常不报 Failed，转 `AwaitingOrderNo`** —— 报失败会骗用户再点一次 → 扣第二份钱
3. **`queryStatus` 只在 `success && data == null` 判 Idle**，请求失败一律 `Unknown`
   —— 误报空闲会让用户站在别人正用的机器前扣自己的钱
4. **`pendingOrder` 防重**，但注释明确写了它挡不住双击并发，**UI 必须自己置灰按钮**

### 板块切换

5. **`same=true` 时一个字段都不动、缓存也不清** —— 这是老用户 4000 洗浴行为不变的唯一保证
6. **切换时拒绝在途订单**（`canLogoutVoluntarily`）—— 在途单绑旧 accountId，切走就关不掉
7. **登录不被板块列表拖住**（`withTimeoutOrNull(4s)`，失败不影响登录成功）

### 设备判定

8. **`deviceKind` bigTypeId 优先**，smallTypeId 只在 big 为 null 时兜底
   —— 历史上 smallTypeId=1 被误当蓝牙特征，导致全校设备开不了阀

### MQTT broker 问题（已知，未修）

`utils/MqttManager.kt:13` 硬编码 `tcp://47.107.37.60:1883`，但吹风机抓包实测是 `39.108.147.136:1883`。

**影响**：`onMqttMessage` 大概率收不到推送 → orderNo 只能走 `lastOrder/byMac` 兜底（慢几秒，但功能不挂）。
**要不要修**（按 projectId 选 broker / 挂双 client）是独立改造，本次没做。

### orderNo 三条路线（实测结论）

| 路线 | 时间窗口 | 现状 |
|---|---|---|
| A. MQTT 推送 | 实时 | broker 不匹配，可能收不到 |
| B. `lastOrder/byMac` | **有窗口**（1h ✅ / 19d ❌） | 已在用，便宜 |
| C. `bill/detail?consumeDate=` | **无窗口**（19 天前也查得到） | **未接入**，最稳的兜底 |

> 路线 C 是 2026-10-24 在线实测发现的，比 B 更可靠（按时刻精确定位，不会取到上一单）。
> 未接入的原因：本地 `placedAtMs` 是手机时间、`consumeDate` 是服务端时间，差几十秒就查不到，
> 需要 ±2 分钟逐秒试探（一次请求变 N 次）。建议做法：**先 B（便宜一次），失败再退 C**。
