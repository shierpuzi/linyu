## 2026-10-29 · #36 流体云胶囊左右不对称：模块矢量图 + 短模块名，设备图标收口到 `DeviceVisual`

### 现象

「按量计费」常驻通知（热水器 / 洗手台 / 饮水机，ID 1001）改之前长这样：

| 胶囊位置 | 改之前 |
|---|---|
| 左侧图标 | 一律一个**水滴**（`ic_notify_shower`）——热水器 / 洗手台 / 饮水机长得一模一样 |
| 左侧文字 | `正在使用 · 卫生间热水器`（完整设备名） |
| 右侧时间 | 系统 Chronometer 自己走秒 ✅（这部分是对的，本次一行没动） |

用户反馈：**左边永远一个水滴，右边一长串设备名被截断，左右不配平**。
并且直接给了改法：「下面两个图标换成当前模块的 xml 矢量图」。

「套餐计费」倒计时通知（洗衣机 / 吹风机，ID 1006）**只有图标这个问题**——
它的标题是「套餐名 · 设备名」，倒计时样式用户已经确认满意，本次不碰。

### 根因不是「图标不好看」，是三件事叠在一起

| # | 问题 | 后果 |
|---|---|---|
| 1 | `Notifier.showInUse` 的 `setSmallIcon` 写死 `R.drawable.ic_notify_shower` | 胶囊左图标不表达「这是哪个模块」，五个模块长得一模一样 |
| 2 | 标题拼的是完整设备名（`shortName(deviceName)`） | 胶囊单侧文本按 OPPO 规范必须精简，长串会被截成「…」；右侧还要放时间 → 左右必然失衡 |
| 3 | emoji → 图标的映射实际有**两份**（`ui/DeviceGlyph` 一份 `when`、`widget/WidgetRenderer` 一份 `when`），而**通知压根没接**，写死水滴 | 两份 `when` 只能靠人肉保持一致，改一处漏一处就是「同一台设备在 App 里是洗衣机、在桌面和胶囊上是热水器」。这个坑 #31 已经在 App↔小组件之间踩过一次 |

第 3 条决定了修法：**不能只在通知里再写第三份 `when`**，那等于把 #31 的坑原地加深一层。
所以先把映射收口成唯一出处，通知只是它的第三个消费者。

### 通知内容对照表（按量计费 · ID 1001）

|---|---|---|

### 为什么标题改成短模块名，而不是保留设备名

| 考虑 | 结论 |
|---|---|
| OPPO 胶囊规范 | 单侧文本要精简，长串被截成「…」——那正是用户看到的「不配平」 |
| 信息是否必要 | 一台设备在用时，设备名是**冗余信息**（用户刚从那个页面退出来，界面里到处都是设备名） |
| 多设备怎么办 | 多台共用一个前台通知位置的场景继续走 `showInUseSummary`（「正在使用 N 台设备」），那里本来就没有单一模块 |
| 设备名去哪了 | `showInUse` 的 `deviceName` 参数**保留**（调用方签名稳定 + 日志排查用），只是不再进标题 |

模块名统一由 `DeviceVisual.moduleName` 出，和 `DeviceInfo.typeName` 的措辞对齐；
但**不依赖设备名**——通知链路上只有 emoji，拿不到 `DeviceInfo`。

### 为什么没有「暂停」按钮（这条写死，别再问是不是漏了）

| 计费模型 | 手上有什么接口 | 能不能暂停 |
|---|---|---|
| 按量（热水器 / 洗手台 / 饮水机） | 只有 `closeOrder` | **不能**。`closeOrder` 一调就真结束并结算，没有「先停一下再继续」这回事 |
| 套餐（洗衣机 / 吹风机） | 连停止接口都没有 | **不能**。下单即扣全款、不可退，服务端到点自动结束 |

所以两种通知都只保留「结束使用」（按量）/「点开查看」（套餐）一个入口。
**放一个点不动的按钮比没有更糟**：用户会以为水停了，其实还在计费。
代码里已经在 `showInUse` 的 builder 链上留了注释说明「这里故意没有暂停按钮」，防止后来人当 bug 修。

### 为什么右侧时间仍然交给系统 Chronometer，不写 `shortCriticalText`

这是 #18 已定案的事，本次**没有推翻，只是照做**——但要说清 #18 管的是哪条通知：

| 通知 | 计时方向 | 时间怎么来 | 写不写 `shortCriticalText` |
|---|---|---|---|
| 1001 按量常驻（热水器/洗手台/饮水机） | 正计时（已用多久） | Chronometer + `setWhen(startAt)` 自己走秒 | **不写**（本次维持原状） |
| 1006 套餐倒计时（洗衣机/吹风机） | 倒计时（还剩多久） | App 每 30s / 1s 重发写文本 | 写（#18 定案，本次不动） |

- 按量一旦写 `shortCriticalText`，就会把走秒**盖成静态串**——那正是 #15/#17 走过六版弯路的起点
- 所以本次只改「标题 / 图标 / 正文」这三块**静态内容**，时间那一路一个字段都没碰
- ⚠️ 两条通知的胶囊规则**不能互相套用**。交接文档那节「胶囊文本永远由 App 提供」
  说的是 1006，本来只对倒计时成立

### 为什么新建 `utils/DeviceVisual.kt` 而不是塞进 `DeviceGlyph.kt`

`ui/DeviceGlyph.kt` 在 **Compose 层**（import 了 `androidx.compose.*`）。
通知（`utils/Notifier`）和小组件（`widget/WidgetRenderer`，RemoteViews）都不能依赖 Compose，
所以两个消费者实际上都拿不到 `DeviceGlyph`。映射必须放在谁也不依赖的 `utils/` 下，
才能被三方共用——这也顺带解释了为什么当初会各写一份 `when`：不是懒，是**位置不对**。

### 验证方式（诚实版）

- 新增 `DeviceVisualTest` 8 个用例，钉住三件事：
  ① 五种设备的图标 id **两两不同**（复制粘贴写错名字时编译不报错，只会在真机上退化成热水器图标）；
  ② 饮水机三个取值（♨️/❄️/🚰）**故意共用**一个图标；
  ③ `null` 与未知值兜底成热水器，**不能返回空串**（模块名会直接拼进胶囊左侧，空串会让一侧凭空缩掉）。
- 本轮只做代码 + 文档，**没有真机验证**。

### ⚠️ 遗留（真机验证清单，别当成已完成）

1. **胶囊是否真的左右配平、模块图标是否真的显示出来** —— 未验证。
   前提仍是那条老规矩：**用户得自己在系统设置里开「流体云 / 实时动态」权限，代码无法代劳**。

3. **套餐倒计时通知只换了小图标**，大图标/标题/正文/胶囊文本全部保持原样。要动它得等用户提需求。

## 2026-10-26 · #35 修跨板块设备开阀报 534「设备信息和项目信息不匹配」

### 现象

用户报告：**收藏的饮水机点开能看、余额也对，但一开阀就弹「开阀失败 / 设备信息和项目信息不匹配」**。
用户之前的绕法「取消收藏 → 扫码 → 再收藏」只是碰巧把当前板块切对了，
不是真的修好。

日志里一次就抓到了（`linyu_log_1793016479783.txt`）：

```
POST /order/tcpDevice/downRate/rateOrder
  xfModel=0&snCode=866061291603&...&projectId=4000&...
resp: {"success":false,"errorCode":534,"errorMessage":"设备信息和项目信息不匹配"}
```

同一份日志里，`GET /device/info/mac` 明确返回这台饮水机
`"bigTypeId":5, "projectId":3356` —— **设备属于 3356，请求却带 4000**。

### 根因

服务端会校验**设备归属**。代码里「查余额」和「下发指令」是两条路，只有前者借对了板块：

| 动作 | 修复前 | 结果 |
|---|---|---|
| 读余额（`loadDeviceBoardWallet`） | 借设备所属板块（`withBoardContext`） | ✅ 显示正确 |
| 开阀 `downRate/rateOrder` | 用当前板块 | ❌ 534 |
| 关阀 `closeOrder` | 用当前板块 | ❌ 534（**更严重：关不掉，水还在流**） |
| 套餐下单 `modeOrder` | 用当前板块 | ❌ 534（点了没反应） |
| 占用/订单查询 `queryUsing` | 用当前板块 | ❌ 534（被判成"空闲/未知"） |
| 结算 `consumeOrderResult` | 用当前板块 | ❌ 查不到金额 |

**这不是饮水机独有**：洗浴板块点洗衣机、洗衣板块点热水器，全部一样。
凡是「设备所属板块 ≠ 当前板块」的操作都会中。

### 改了什么

| 文件 | 内容 |
|---|---|
| `data/DeviceBoardPolicy.kt` | 新增 `operationBoard()`：只比「设备板块 vs 当前板块」相不相等；**删掉了 `BATH_PROJECT_ID = 4000L` 硬编码兜底** |
| `data/ProjectRepository.kt` | 新增 `withDeviceBoard()`：在设备所属板块的认证参数下执行操作，`finally` 必定还原。同板块 / 判断不出 → **直接透传、零开销** |
| `model/ActiveOrder.kt` | 增加 `projectId`：关阀时手上只有 `snCode`，靠它才选得对板块 |
| `utils/PrefsHelper.kt` | 增加 `lastDeviceProjectId`（桌面小组件那条只有 `snCode` 的路径要用） |
| `data/ShowerController.kt` | 534 转成可读提示，不再原样抛服务端文案 |
| `ui/MainViewModel.kt` | 开阀/关阀/下单/占用轮询/结算/状态查询全部包进 `withDeviceBoard`；`routeAfterDeviceInfo` 记下设备归属 |
| `service/ShowerWatchService.kt` | 后台监控的 `queryUsing` / 关阀 / 结算同样按设备板块执行 |
| `widget/LinYuWidgetProvider.kt` | 小组件开阀按 `lastDeviceProjectId` 选板块 |

### 关于「各校 projectId 编码不同」（这条最重要）

用户明确提出：**别的学校不一定是 4000/3356 这套编码**。
所以这次修复**刻意不含任何硬编码 id**：

| 场景 | 行为 |
|---|---|
| 单板块学校 | 设备 projectId == 当前板块 → **零开销透传，行为与修复前完全一致** |
| 多板块 · 同板块 | 同上，不碰全局认证参数 |
| 多板块 · 跨板块 | 切到设备那个板块 |
| 设备没报 `projectId` | 返回 null → **保持当前板块，一个字段都不动** |
| 换成任意其它 id（如 9991/7777） | 照样正确，判定只比相等 |

**顺带删了 `DeviceBoardPolicy.BATH_PROJECT_ID = 4000L`**：那是「判断不出就猜本实测校的洗浴」
的兜底，换学校就是错的 id（要么查出不存在板块一直加载中，要么显示别人的钱）。
判断不出时改为**不显示余额**，这是有意的降级。

### 验证方式

```
:app:testDevDebugUnitTest  → 31 套件 / 258 用例 / 0 失败
:app:assembleDevDebug      → BUILD SUCCESSFUL，app-dev-debug.apk 22.3 MB
```

- `DeviceBoardPolicyTest`：跨板块判定、同板块零开销、判断不出不切

- `DeviceBoardOtherSchoolTest`：**用编造的 9991/7777 证明不依赖 4000/3356**

### ⚠️ 还没做的（真机验证）

编译和单测只能证明「代码按预期切换了板块」。**「服务端是否真的接受借来的板块参数」
必须真机实测**——这是整个修复的成败点：

1. 切到洗浴板块 → 点收藏里的饮水机 → 开阀，应当不再报 534
2. 开完后关阀，确认能正常结算（关不掉比开不了更严重）
3. 停在洗浴板块 → 点洗衣机 → 下单，确认不报 534

### 遗留

1. 上述三项真机验证未做
2. 本次修复在分支 `fix/cross-board-534` 上，**master 未合入**（用户要求不碰 master）
3. 蓝牙水表（`ble/`）那条通道没动：它走 `bluetoothRateOrder` 等接口，
   是否也校验项目归属**未验证**，但蓝牙表通常与当前板块一致，风险低

## 2026-10-24 · #29 收藏路径进设备页余额还是错的（#28 只修了一半）

**用户报的**：「从『上次使用设备』进入显示的余额是正确的，但从『收藏设备』路径
进入的余额算法没写上去；修 bug 修一半」

**根因：我只在入口 `openMeteredScreen()` 里加了一次调用**

#28 把 `loadDeviceBoardWallet()` 挂在 `openMeteredScreen()` 上，只覆盖了两条路：

| 入口 | 怎么拿 DeviceInfo | 有 projectId 吗 |
|---|---|---|
| 上次使用 | `DeviceInfoCache.load()` 联网查台账 | ✅ 有 → **余额正确** |
| 收藏设备 | `fav.toDeviceInfo()` 用本地快照还原 | ❌ 快照没存 → 回退当前板块 → **余额错误** |

收藏是**离线快照**（设计上要能离线渲染），而 `FavoriteDevice` 里根本没存 `projectId`。
「两条路表现不一致」正是这个原因。

**改了什么**

| 文件 | 改动 |
|---|---|
| `data/FavoriteStore.kt` | `FavoriteDevice` 新增 `projectId` / `projectName`；`toFavorite()` / `toDeviceInfo()` 双向带上 |
| `ui/MainViewModel.kt` | `selectedDevice` 改为**自定义 setter**（底层仍是 `mutableStateOf`），赋值即触发 `loadDeviceBoardWallet()` |
| `ui/MainViewModel.kt` | `openFavorite()` 对**老收藏条目**（`projectId == null`）补一次台账查询校正归属 |
| `ui/MainViewModel.kt` | 移除各处重复的显式调用；顺手补 `startLastDevice()` 两条分支（它直接进使用中页面，原来也没取余额） |
| `test/.../FavoriteStoreTest.kt` | 新增 3 个用例（归属保留、JSON 往返、老数据不崩） |

**关键改动：收口到 setter，而不是继续加调用点**

```kotlin
private var selectedDeviceState by mutableStateOf<DeviceInfo?>(null)

var selectedDevice: DeviceInfo?
    get() = selectedDeviceState
    set(value) {
        selectedDeviceState = value
        if (value != null) loadDeviceBoardWallet(value)
    }
```

`selectedDevice` 有 5 处以上赋值点（扫码、点附近设备、点收藏、点上次使用、
从活跃订单恢复）。逐个补调用注定会漏——这次就是这么漏的。收口到状态变更本身，
以后新增入口不会再漏。

⚠️ **底层必须仍是 `mutableStateOf`**：只写普通字段（`var selectedDevice = null`
+ 自定义 setter 用 `field`）的话界面**不会重组**，设备页会停在上一台设备的内容上。

**代价**：赋值时会顺带发一次请求，但只在**跨板块**时才真发
（同板块直接复用 `walletBalance`，见 `DeviceBoardPolicy.needsBorrow`）。

**老数据兼容**：已有收藏条目没有 `projectId`，Gson 留 null → 走「补查台账」那条路，
查不到就退回旧行为（当前板块），不崩。

**验证方式**
- 223 → 226 用例通过（`FavoriteStoreTest` 新增 3 个）
- APK 字节扫描确认无凭证泄漏

**教训**
1. **同一个逻辑有多个入口时，不要在入口上加调用，要收口到状态/数据源头**
2. 我上一轮的修法就是典型的「按报告的现象打补丁」——只修了用户截图那条路。
   正确做法：把 `selectedDevice` 的所有赋值点列一遍（`grep 'selectedDevice ='`），
   确认每个入口的 `DeviceInfo` 是否都带 `projectId`
3. 这条正好是 `AGENTS.md` 里那句的实例：「报告给的是症状，要 grep 所有 caller，
   在共享函数里修一次」——我第一轮没照做，于是交付了半成品

## 2026-10-24 · #26 新增 loginCode 登录（粘码直登，免短信验证码）

**用户要的**：新增一种登录方式，直接粘 `loginCode` 登录，并放一个抓包教程超链接。

**其余参数全自动解析**：`/user/project/list` → `accountId` + `projectId`；
`/account/info` → `telephone`。用户只填两个字段。

**改了什么**

| 文件 | 改动 |
|---|---|
| `ui/LoginCodePolicy.kt` | **新增**，纯逻辑：32 位 hex 校验、`normalize`、从**整条抓包 URL** 里抠 `loginCode`/`userId` |

| `ui/LoginViewModel.kt` | 新增 `isCodeMode` / `switchCodeMode()` / `codeLogin()` |
| `ui/LoginScreen.kt` | 三模式切换 + 两个输入框 + 抓包教程超链接 |
| `test/.../LoginCodePolicyTest.kt` | **新增** 6 个用例 |

**两处防坑（都是自查发现的）**

1. **先校验再落盘**：任何一步失败都不写 Prefs。否则会进到「半登录」状态

## 2026-10-24 · #18 定案 v5：胶囊文本**永远**由 App 提供（ColorOS 不支持 when 回退）

**用户实测反馈**：「大于2分钟还是这个样子，没有剩余 3 分钟；小于两分钟还正常」。

## 这推翻了我 v4 的核心假设

v4 我按官方文档做的：**剩余 ≥2 分钟时让系统按 `when` 自动渲染**，App 不写 `shortCriticalText`。
文档原文确实写着：
> The when time is at least 2 minutes in the future: 胶囊显示 `5min`。

**但 ColorOS 16 实测不实现这条回退**：不写 `shortCriticalText` 时，
胶囊只有通知标题、没有时间。而 <2 分钟时因为 App 写了文本，反而正常。

所以「前段没时间、后段正常」这个分裂现象，正是我 v4 的**双模式判断**造成的。

**教训：官方文档描述的是 AOSP 行为，OEM 可以不实现。以真机为准。**

## 改了什么

| 文件 | 改动 |
|---|---|
| `NotifyTextPolicy.chipText()` | **新**：永远返回非 null。≥2分钟给 `3分`/`1时2分`，<2分钟给 `01:30` |
| `NotifyTextPolicy.preciseChipText()` | 删除（它允许返回 null，正是 v4 的错误入口） |

**粒度设计**

| 剩余 | 胶囊 | 例 |
|---|---|---|
| ≥ 2 分钟 | 分钟级 | `3分` / `13分` / `1时2分` |
| < 2 分钟 | 秒级 mm:ss | `01:30` / `00:45` |

## 2026-10-24 · #17 定案 v4：前段交系统（分钟级）+ 最后 2 分钟 App 供秒级

**用户决策**：「最后 2 分钟：App 提供秒级，能看到精确剩余」

## 为什么是 2 分钟（不是随便定的）

官方文档《创建实时更新通知》对 `when` 驱动的胶囊有明确门槛：
> The when time is at least **2 minutes** in the future: 当前 10:05、when 设 10:10，胶囊显示 `5min`。
> **The when time is in the past: The text isn't shown.**

即 **剩余 ≥2 分钟系统才渲染时间**（分钟级，同竞品「13分钟」）；
低于 2 分钟就不显示时间——用户看到的是「胶囊只剩个标题」。

> 用户 10:58 的截图正是这个：测试通知只剩 1.3 分钟，胶囊只有标题没有时间。

| ≥ 2 分钟 | **系统**（按 `when` 算） | 30 秒 | 分钟级（向上取整） |
| < 2 分钟 | **App**（写 `shortCriticalText`） | **1 秒** | **秒级** |

## 2026-10-24 · #16 定案：胶囊交给系统渲染，文案按分钟

**用户反馈**（第三次）：1 秒版「不太顺滑」，并指出竞品是**按分钟**的：
> 我看其它第三方做的是按分钟计算，不精确到秒；或许我们早该这么做了

截图证据：外卖胶囊是「**送货中** | **13分钟**」——标签 + 分钟数，没有秒。

**纠正我上一轮的错误结论（重要）**

#15 里我断定「ColorOS 必须有 `shortCriticalText` 才提升」，理由是「去掉它后
`PROMOTED_ONGOING` flag 消失」。**这个结论是错的**——那次测试发生在 10:26，
而**用户 10:28 才手动打开「流体云显示实时状态」权限**。两条依赖被搅在一起了。

权限开来后重测：**去掉 `shortCriticalText`，`PROMOTED_ONGOING` 照常出现**，
`showWhen=true` 也在。系统会自己按 `when` 算出「还剩 N 分钟」。

**所以正确做法早就在 AOSP 文档里**：
> If setShowWhen(boolean) is true, the chip content will be the time remaining
> until Notification.when, if positive.

竞品（外卖「13分钟」、打车）全是这条路——**系统渲染的分钟级倒计时，自己会走，不用重发**。

**改了什么**

| 文件 | 改动 |
|---|---|
| `NotifyTextPolicy.REFRESH_INTERVAL_MS` | `1_000` → **`30_000`**（只刷新正文文字） |
| `NotifyTextPolicy.remainingLine` | 改成**分钟级 + 向上取整**：`剩余 3 分钟`、`剩余不到 1 分钟` |
| `NotifyTextPolicy.elapsedLine` / `minuteGranularity` | 新增，正向计时也用分钟级 |
| `NotifyTextPolicy.chipText` / `elapsedChipText` / `CHIP_MIN_SEC` | **删除**（见下） |
| `Notifier.showModeOrderRunning` | `.requestLiveUpdate()` 不传 chipText |
| `Notifier.showInUse` | 同上，正文用 `elapsedLine` |
| `test/.../NotifyTextPolicyTest.kt` | 重写：20 个用例，含「文案里不能出现秒」的断言 |

**为什么删掉 `chipText`**：它的职责是算「胶囊里那个 `02:58`」。但胶囊不该由 App 提供文本，
留着它只会诱使人再写进 `shortCriticalText`、把系统倒计时盖成静态串。
**代码里不留诱饵。**

**实测验证**

```
# 通知状态（权限已开的情况下，不写 shortCriticalText）
flags=ONGOING_EVENT|ONLY_ALERT_ONCE|PROMOTED_ONGOING   ← 提升正常
android.showWhen=Boolean (true)                        ← 系统据此算剩余时间
android.requestPromotedOngoing=Boolean (true)
（没有 android.shortCriticalText）                      ← 交给系统

# 30 秒刷新仍工作
T0:    timeout=PT4M
T+35s: timeout=PT3M29S
日志: 10:58:24 重发，剩余 149s（剩余 3 分钟），胶囊交给系统

# 自动消失仍工作
日志: 10:44:57 套餐倒计时自刷新：到点，撤通知
```

**最终形态**
- 胶囊：系统渲染「还剩 N 分钟」，自己走，不用重发
- 正文：`¥0.60 · 剩余 3 分钟 · 到点自动结束`，30 秒刷一次
- 到点：`setTimeoutAfter` + 自刷新循环双保险撤通知

**关键取舍：代码里不留诱饵**

删除 `chipText()` 不只是清理死代码——它是个**陷阱**：
任何人看到「胶囊文本生成器」都会想把它写进 `shortCriticalText`，
而那正是把系统倒计时盖成静态串的原因。删掉它，正确路径就是唯一路径。

**教训（写给自己）**
1. **测试结论前先确认前置条件是否都满足**。我把「权限没开」和「extras 不对」混在一起，
   得出「ColorOS 必须给文本」的错误结论，白走了一轮 1 秒重发的弯路
2. **用户说「竞品怎么做的」时，应该先去查竞品的行为**，而不是继续调自己的参数

## 2026-10-24 · #15 胶囊倒计时终于每秒走了（30 秒 → 1 秒）

**用户实测反馈**：改完 #14 后胶囊确实动了，但**每 30 秒才跳一次**（`3:00 → 2:29`）。
用户提示：「实在不会做，看看官方时钟 app 的倒计时那边怎么做的」。

**调研结论（三个关键事实）**

1. **[AOSP 文档](https://developer.android.google.cn/reference/android/app/Notification.Builder)明确胶囊优先级**：
   > Short critical text will always be **the highest precedence content for a chip**.
   > A time (from Notification.when) is the final source of content.
   > If setUsesChronometer(true) is true, the chip content will be a chronometer.
   > If setShowWhen(true) is true, the chip content will be the time remaining until when.

   → **写了 `shortCriticalText` 就会盖掉 Chronometer**，胶囊变成静态串。

2. **实测：去掉 `shortCriticalText` 后 `PROMOTED_ONGOING` flag 消失**
   → 说明 **ColorOS 16 不认 `when` 作为胶囊内容来源**，它要求胶囊必须有显式文本。

3. **Android 通知限流是「每秒 10 次」**（Nougat 起）。
   超过会打印 `Package enqueue rate is X. Shedding events.` → 所以 1 秒 1 次安全。

| 文件 | 改动 |
|---|---|
| `utils/NotifyTextPolicy.kt` | `REFRESH_INTERVAL_MS`：`30_000` → **`1_000`**，注释写清两侧约束 |
| `Notifier.kt` `requestLiveUpdate` | 保留 `chipText`（ColorOS 需要），补注释「别删」 |
| `test/.../NotifyTextPolicyTest.kt` | 3 个节流用例改 1 秒口径 + 双向边界断言 |

**实测验证（日志证明每秒在跳）**

## 2026-10-24 · #14 倒计时通知三处修复（负数不消失 / 胶囊不倒数 / 一直挂着）

**用户报的现象**
1. 通知栏的倒计时**变成负数也不结束通知**
2. 上滑回来打开「流体云显示实时状态」后出现胶囊 `3:00`，但**不跟着倒计时**
3. 通知一直挂着

**根因（ADB 实测确认）**

| # | 现象 | 根因 |
|---|---|---|
| 1 | 负数不结束 | `setOngoing(true)` 的通知**系统永不自动撤**；`Chronometer` 过了 `when` 继续往下数成 `-00:17`。撤通知的责任在 `viewModelScope` ticker，App 退后台/被杀就没人撤 |
| 2 | 胶囊 3:00 不动 | `shortCriticalText` 是**发通知那一刻写死**的，要更新只能重发整条通知。测试按钮**只发一次、不启动任何刷新循环** |
| 3 | 一直挂着 | 同 #1 |

**实测证据**（10:08 抓到的一条）
```

现在 = 2026-10-24 10:08:20
已过期 1070 秒（17 分钟），通知还挂着
```

**改了什么**

| 文件 | 改动 |
|---|---|
| `utils/Notifier.kt` `showModeOrderRunning` | 加 `.setTimeoutAfter((remainingSec + 60) * 1000L)` —— 交给**系统计时**，进程死了照样撤 |
| `utils/Notifier.kt` 新增 `startModeOrderAutoRefresh()` | `Handler` 每 30 秒重发通知刷新正文和胶囊；到点自动撤。**不依赖界面存活** |

| `debugProbeModeOrder` | 也启自刷新（否则测试按钮发的通知同样会卡死） |

**为什么不用 `viewModelScope` 做循环**：用户点完测试按钮直接退出设置页，ticker 根本没启动。
Handler 挂主线程，至少不依赖界面；进程真被杀就靠 `setTimeoutAfter` + 启动时兜底。

## 2026-10-24 · #9 通知真根因：渠道懒加载 + 向不存在渠道发通知会被静默丢弃

**改了什么**
- `MainActivity.kt` 加 `Notifier.ensureChannels(this)` —— **启动就建渠道**
- 渠道 id 改 `linyu_mode_order_v2`（旧 id 属性已固化，改不回来），并删除作废的旧渠道
- **去掉 `setBypassDnd(true)`**（用户选了「方案 A：让它安静待着」）
- `refreshPendingFrom` 三层 `?.let` 拆开逐步记日志

**为什么（这是我上一轮"修了个寂寞"的真正原因）**

上一轮我认定是「勿扰拦截」，改了 `setBypassDnd(true)` 就说修好了 —— **没验证**。
这次用 ADB 一步步查，真相是两个叠加的问题：

1. **`setBypassDnd(true)` 被系统静默忽略**：需要 `ACCESS_NOTIFICATION_POLICY`
   特殊权限（manifest 没声明，且只能用户手动授）
2. **更致命的一条**：`ensureChannels` 是**懒加载**的，只在 `Notifier.xxx()` 内部调。
   而 **Android 8+ 向不存在的渠道发通知会被静默丢弃**（不报错）。
   于是首次发通知 → 渠道不存在 → 丢弃 → 渠道也没建出来 → 日志里连痕迹都没有。

我看到的 `numEnqueuedByApp=5` 是**旧进程的累积值**，误以为「发了但被拦」，判断方向完全错了。

**验证**：启动后 `dumpsys` 里必须有 `linyu_mode_order_v2`；
App 日志必须有「套餐倒计时渠道就绪」。

**教训（写给自己）**
1. **改完必须验证**，不能"改完 + 编译通过"就当修好了
2. 排查通知问题**先看渠道是否存在**，再看权限、再看勿扰
3. `numEnqueuedByApp` 是**进程累积值**，重装后要按新 pid 看
