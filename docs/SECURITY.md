# 安全说明

本文说明**趣智Lite**（原名「淋浴」/ LinYu）在安全方面做了什么、没做什么，以及**你该如何确认自己装的是正版**。

> 一句话版本：**只从下面列出的官方渠道下载。** 别人重新打包的版本可能带后门，而且——见第二节——**光对签名指纹拦不住这种情况**。

## 一、从哪下载

官方只有 **GitHub** 一个渠道：

| 渠道 | 地址 | 说明 |
|---|---|---|
| **GitHub**（唯一官方源） | https://github.com/shierpuzi/linyu/releases | 源码仓库，发行版在这里发布 |

⚠️ **Gitee 镜像已停用。** 仓库里 `api/GithubApi.kt` 的 `GITEE_REPO` 已被置为空串，App 内的「检查更新 / 下载安装包」因此走 GitHub 直链（`objects.githubusercontent.com`）。代价是大陆实测速度只有 **约 100 KB/s**——慢，但这是目前唯一能确认来源的地址。若以后恢复镜像，会先在这里和更新日志里说明。

- 打着「去广告版」「破解版」「优化版」旗号的版本

## 二、怎么确认你装的是正版

### 这一节必须先说清楚一件事

**v3.2.1 起，正式版 `com.quzhi.lite` 是真正的 release 签名包了。**

在这之前（v3.1.0-dev 及更早的公开测试版）发布的是 debug 签名产物——那时仓库里没有配 release keystore，`app/build.gradle.kts` 走「Release 包保持未签名」的分支，实际发的是 `assembleDevDebug` 出来的东西。

现在情况变了，但**结论没有变**：

> **核对签名只能告诉你「这个 APK 和官方发出去的那份是同一个包」（比如更新时不会被换成别人的），不能告诉你「它是正版」。**
>
> release 密钥确实比 debug 密钥强——它不随构建机生成、不会每次编译都换一个。**但它仍然只是一把密钥**：别人完全可以自己生成一把密钥，给他的改包签上名，那份包在我们这种核对方式下同样「签名自洽」。
>
> **所以：签名不是身份凭据，下载渠道才是。**

### 当前正式版的签名（`com.quzhi.lite`）

| 项 | 值 |
|---|---|
| 包名 | `com.quzhi.lite`（正式版，无 `.dev` 后缀） |
| 版本 | `versionCode 18` / `versionName 3.2.1` |
| 签名类型 | **release**（RSA 2048 / SHA384withRSA，有效期至 2054-03-16） |
| 证书主体 | `CN=QuzhiLite, OU=Personal, O=shierpuzi, C=CN` |
| **证书 SHA-256** | `81:7F:13:F0:56:B0:08:1F:C2:36:83:74:31:5F:BD:7C:CD:8E:0C:8B:AC:7C:2C:04:06:7E:21:EC:A5:AE:BA:E7` |
| 证书 SHA-1 | `288728bc4eedb6fb4d5dcd56cb112a12bdd55947` |
| 预置凭证 | **无**（store flavor 的 `PREFILL_*` 显式给空串，`verify_apk.py` 会验证） |

自己核对：

```bash
apksigner verify --print-certs 趣智Lite-v3.2.1.apk
```

> 文件名按发布时的习惯写（本地构建产物叫 `app-store-release.apk`，Release 附件可能改名）。
> **核对的是指纹，不是文件名**——所以先确认你手上的包是 `com.quzhi.lite` + `versionName 3.2.1`，再对指纹。
> 查包名/版本：`aapt dump badging 你的文件.apk | findstr package`。

`apksigner` 随 Android SDK 提供（`%ANDROID_HOME%\build-tools\<版本>\apksigner.bat`）。输出里的 `Signer #1 certificate SHA-256 digest` 应与上面那一长串**逐字符相同**（大小写、冒号都无关）。部分手机（小米、华为等）在「设置 → 应用 → 趣智Lite → 应用详情」里也能看到签名信息。

> ⚠️ **指纹对不上不等于被篡改，先看版本**：dev 测试包永远是 debug 签名（指纹每次构建都可能不同），旧版本的包也各不相同。
> 只有「`com.quzhi.lite` + 某个正式版本号」才应该对上这把指纹。

### 测试包（`com.quzhi.lite.dev`）仍是 debug 签名

这不是漏配，是**故意的**：它本来就是个可共存的测试分包，用独立通道（只收 pre-release），不该被拿来当正式版。

| 项 | 值 |
|---|---|
| 包名 | `com.quzhi.lite.dev`（dev flavor，可与官方趣智校园 App 共存） |
| 版本 | `versionCode 18` / `versionName 3.2.1-dev` |
| 签名 | **debug** |
| 预置凭证 | **无**（构建时临时清空 `local.properties`，装上去必须自己登录） |

### 密钥是怎么保管的（以及为什么你要相信这一段的边界）

- keystore 文件 `quzhi-lite-release.jks` **不在本仓库内**，也不在任何公开仓库里——它放在开发者的项目目录之外。
- 另有一份**加密备份**（AES-256，外层密码不在仓库里）存在私有仓库 `shierpuzi/quzhi-lite-keys`。
- 仓库里**只有本文这一串公开指纹**，不包含任何密钥材料，更不包含密码。

> 说白了：**这把密钥的安全性依赖于维护者本人**。本文能承诺的是「指纹公开、便于核对」，不能承诺「握有指纹的人就一定是官方」——见本节开头那句结论。

### 历史签名指纹（原样保留，未改动）

本文旧版记录过一组 release 密钥指纹。从证书主体里的 `Hualala` 和 `LinYu` 看，它属于**改名之前**（包名还是 `com.hualala.linyu`）那批发行版的签名密钥——`docs/CHANGELOG.md` 里从 v2.1.0 到 v3.1.0 的每一段版本信息都记着「构建类型：Release（R8 混淆 + 签名）」，可见那时候确实是有 release keystore 的。

```
证书主体 : CN=Hualala, OU=LinYu, O=Hualala, L=Jinhua, ST=Zhejiang, C=CN

SHA-256 : ccaf8d04aa73a3b3d04a9e0d3abba3d89f8217d411b543f4b563dd3fa2e7e41a
SHA-1   : 33df7934bb508301ff768804f322b961af74752e
MD5     : e30d8bec533ae579f1a6a6698e865c15
```

⚠️ **它对现在的发行版用不上，原因有两个：**

1. 改名后包名换成了 `com.quzhi.lite`，而**现行发布用的是另一把密钥**（指纹见上，主体是 `QuzhiLite` / `shierpuzi`）——改名前后不是同一把。
2. 仓库里**没有入库任何 `.jks` / `.keystore`**，也没有记录旧密钥对应哪几个历史文件——所以无法用它核对任何一份现存产物。

结论：**从 Releases 下到的包对不上这组指纹属于正常情况，不代表被篡改**；反过来，手上一个包如果真能对上它，说明那是改名前的旧版本，也不代表就是当前版本。留着这组值只是不让它凭空消失——**不要拿它当现在版本的判据**。

### 那你能验什么

**能验的：** 某个具体版本、某个具体渠道下到的包，有没有在传输过程中损坏 / 被换掉。

```bash
# Windows
certutil -hashfile 趣智Lite-v3.2.1.apk SHA256

# Linux / macOS
sha256sum 趣智Lite-v3.2.1.apk
```

和发行版页面上的说明比对。**这个方法只在同一版本内有效**，新版发布后旧值就失效了。

**App 内更新还多做了一层：** 下载完成后先核对附件长度；GitHub Release 提供 `sha256` 摘要时会再校验一次文件摘要；调起安装器前还会确认更新包的**包名与当前应用一致**、**签名证书的 SHA-256 与已装应用一致**，任一不符直接阻止安装（`utils/ApkUpdater.kt` 的 `verifyApkIdentity`）。这条校验**不会因为摘要拿不到而降级跳过**。

> 这一层在有了 release 签名之后更实在了：同一个正式版号下，密钥不会变，所以「签名不一致」是个真信号。

**签名怎么自己看**（想确认装的确实是发行版里那个文件时用）：

```bash
apksigner verify --print-certs 趣智Lite-v3.2.1.apk
```

`apksigner` 随 Android SDK 提供。部分手机（小米、华为等）在「设置 → 应用 → 趣智Lite → 应用详情」里也能看到签名信息。

## 三、为什么不要装别人打包的版本

**这是第三方客户端最大的现实风险，而且和你用不用这个 App 无关——它取决于你从哪里下载。**

### 重新打包能做什么

任何人拿到我们的 APK 后，都可以：

1. 反编译，插一段代码
2. 重新签名
3. 发到各种渠道

**技术上没有任何门槛**，而且改过的包**外观、功能、界面可以做到和正版一模一样**。

### 插进去的代码会干什么

常见的几种：

| 手段 | 后果 |
|---|---|
| 在登录页加一行上报 | **你的账号密码直接发到攻击者服务器** |
| 替换内置的更新地址 | 让你一直装他们的版本 |
| 加广告 SDK / 引流 | 你的设备被拿去刷量 |
| 加远控后门 | 手机被远程控制 |

第一种最常见，也最致命。

### 为什么我们的包容易被盯上

这个 App 的用户是**在校学生**，账号往往和其他校园系统共用一套密码。一个改过的安装包，可能一次收到成百上千个真实的校园账号。

**所以：不要把安装包转发给别人，也不要装别人转发的安装包。** 要分享就直接发官方链接。

### 我们能做的防御（以及它的边界）

v3.2.1 起正式版有了固定的 release 签名，所以情况比之前好一点，但**只好了半步**：

- **能防的**：App 内更新会比对包名与签名证书摘要，不一致直接阻止安装。所以**没人能用改包把你「更新」成他的版本**——这一条现在是真成立的（同一把 release 密钥，指纹稳定）。
- **能防的（新增）**：你可以自己 `apksigner verify --print-certs` 核对指纹，确认手上这个包和官方发布的那份同源。
- **防不了的**：**第一次安装**，以及「指纹对得上就等于正版」这个推断本身。别人造一个包、用他自己的密钥签，指纹照样自洽且稳定——他只是和官方不一样而已。你要么从 GitHub Releases 下，要么就是在信别人的渠道。
- 本文第二节已经写了真实指纹，所以**这一层现在算是有了**；但它换来的是「可核对同源」，不是「可证明身份」。

## 四、我们的安全设计

### 1. 没有后端服务器 —— 这是最根本的一条

趣智Lite **没有自己的服务器**。你的账号密码从手机**直接发到趣智校园官方接口**（`https://v3-api.china-qzxy.cn`），中间不经过任何我们控制的机器。

意味着：

- 我们**看不到**你的密码、手机号、消费记录
- 我们**存不下**你的任何数据
- 就算我们的仓库被黑，攻击者也拿不到用户数据——**因为根本没有**

这也是为什么本 App 能做到「只装一个 APK 就能用」：没有服务端要维护。

> 补充一句：App 里也没有接任何统计 / 崩溃上报 SDK。日志只写本机文件，导不导出由你决定。

### 2. 密码不落盘

```
输入明文 → MD5 后取 10 位 → 转大写 → 发出去 → 立即清空内存里的明文
```

说准确一点：明文在你输入之后会**一直留在登录页的内存状态里**（`ui/LoginViewModel.kt` 的 `password`），直到登录返回——成功或失败都会立刻把它置空（`LoginSecretPolicy.clearPassword`）。所以它存在的时间是「你输入到登录完成」这一段，不是几毫秒，但**全程不碰磁盘**。

`utils/PrefsHelper.kt` 里**没有任何 password 字段**（全文件搜不到 `password` / `pwd`），密码不会被写进任何本地存储。重装 App、清除数据，都不会留下密码痕迹。修改密码时同样只做一次 MD5 就发出去（`utils/MD5Utils.kt`）。

### 3. 全站强制 HTTPS

`network_security_config.xml` 里默认**禁止一切明文流量**：

```xml
<base-config cleartextTrafficPermitted="false">
```

唯一的例外是趣智校园的 MQTT 服务器 `47.107.37.60`（原因见下方「已知暴露面」）。

### 4. 敏感数据加密存储（但有一条降级路径）

`loginCode`、`userId`、`accountId`、`telephone` 等会话凭证，以及**姓名、学号、一卡通/钱包余额**，
全部存在 **EncryptedSharedPreferences** 里（`linyu_prefs`），由 Android Keystore 托管密钥。
**手机被 root 之前，这些数据是解不开的。**

> ⚠️ 前提是加密初始化成功。极少数设备上 Keystore 不可用时会退回**明文**文件 `linyu_prefs_plain`——这一点写在第五节第 7 条，不再重复美化。

同时，这两份 prefs 文件和 App 日志都被排除在云备份 / 设备迁移之外（`backup_rules.xml`、`data_extraction_rules.xml`），不会顺着系统备份跑到别的设备上。

> 这些都只是为了**显示**——不显示姓名学号、不显示余额，App 其余功能照常可用。

### 5. 日志自动脱敏

App 内置日志导出功能（方便排查问题），但**写入前会自动打码**（`utils/AppLogger.kt`）：

| 字段 | 处理 |
|---|---|
| 手机号 | 保留前 3 后 4，如 `191****2082` |
| password / loginCode / secret / telPhone / telephone / smsCode / useCode / userId / accountId / code | 整个值替换成 `***` |
| 设备 `snCode` | **不打码**（它是排查结算问题时唯一能把日志和账单对上的线索） |

而且 **HTTP 访问日志只记录路径，不记录查询串**（`appLogInterceptor` 记的是 `req.url.encodedPath`，GET 请求又没有 body）——所以 `loginCode` / `telephone` 这类放在 URL 里的凭证**不会进日志文件**。

但**不要把「脱敏了」理解成「什么都不会泄露」**：响应片段（最多 400 字符）里可能有姓名、学号、余额、订单号，脱敏规则不一定覆盖到。导出前自己扫一眼，见下一条。

### 6. 网络排查日志在 Release 与 Debug 里的差异（含当前发行版的实际状态）

`HttpLoggingInterceptor` 的 BODY 级别完整日志**只在 Debug 构建里存在**（`api/NetworkModule.kt` 里受 `if (BuildConfig.DEBUG)` 包着）。

项目自己的日志拦截器（`appLogInterceptor`）在**所有构建类型**里都会记：接口路径、请求耗时，以及最多 300 个字符的请求片段和 400 个字符的响应片段。运行时片段写入前会经过上面的脱敏规则，但脱敏只覆盖已知字段和格式，**不能保证识别所有敏感内容**。**导出分享前请自行检查，并只发送给可信的维护者。**

> ⚠️ **发行版的实际状态**：正式版 `com.quzhi.lite` 是 **release 构建**，所以上面那段 BODY 级完整日志**在正式版里不存在**；dev 测试包 `com.quzhi.lite.dev` 是 `assembleDevDebug` 出来的 debug 构建，**它是开着的**——会连请求体一起写进本机日志文件。脱敏规则照常生效，但这是 debug 包的代价，装测试包的人应该知道。

### 7. 代码混淆与资源压缩（正式版已生效）

`app/build.gradle.kts` 里 Release 构建启用了 R8（`isMinifyEnabled = true` + `isShrinkResources = true`），代码标识符混淆、无用代码剔除。

- **正式版 `com.quzhi.lite`**：这是 release 构建，R8 生效，包体从 21 MB 级降到 **12.77 MB**。反编译出来不再是和源码同构的样子。
- **dev 测试包 `com.quzhi.lite.dev`**：仍是 debug 构建（`buildTypes.debug` 没开 minify），**类名和方法名都是原样的**。

> 但别把混淆当安全边界：它只能抬高逆向门槛，抬不高多少——`utils/KlcxkjCrypto.kt` 那两把密钥反编译一下照样能拿到（见第五节第 6 条）。

### 8. 更新包校验

应用内更新**只读 GitHub Release**（`api.github.com/repos/shierpuzi/linyu/releases`），**不信任何第三方更新服务器**，也不读任何可被替换的更新地址。Gitee 镜像已置空，下载走 Release 附件直链。

下载完成后会先核对附件长度；如果 GitHub Release API 提供 `sha256` 摘要，还会校验文件 SHA-256。国内网络可能访问不了 `api.github.com`，摘要取不到时不会阻止下载——但**签名校验不会因此降级**。

无论摘要是否可用，调起安装器前都会确认更新包的包名与当前应用一致，并比较双方签名证书的 SHA-256 摘要。包名、签名不一致或签名无法读取时会直接阻止安装。

## 五、已知暴露面（诚实披露）

下面这些是**真实存在的**，我们写出来而不是藏着——因为其中大部分**不是我们能在 App 端解决的**。

### 1. 会话令牌出现在 URL 查询串里

趣智校园的官方 API 要求 GET 请求把认证参数**放在 URL 里**（`api/NetworkModule.kt` 的 `authInterceptor` 会给每个 GET 追加）：

```
GET /account/wallet?loginCode=xxx&userId=xxx&accountId=xxx&projectId=xxx&telephone=xxx&...
```

这意味着 URL 可能被**代理日志、服务器 access.log、CDN 日志**记录；你用抓包工具排错时截的图里也会带着它。

**为什么改不了**：这是官方接口的协议设计，第三方客户端只能遵循。改成 POST 服务端不认。

**影响**：需要攻击者能接触到上述日志才有意义，普通用户不受影响。**App 自己的日志不会记查询串**（见第四节第 5 条）。

### 2. MQTT 实时推送走明文，而且 broker 硬编码、各校不通用

```kotlin
// utils/MqttManager.kt:13
private val serverUri = "tcp://47.107.37.60:1883"    // 不是 ssl://
```

三件事叠在一起：

1. **明文**：趣智校园的 MQTT 服务器不支持 TLS，推送内容（订单状态、消费金额）在传输中未加密，同一 WiFi 下的攻击者理论上可以嗅探。
2. **连接不带任何凭证**：代码里没有用户名 / 密码，主题名就是手机号——`app_downRate_<手机号>`、`app_shutdownOrder_<手机号>`、`app_uploadData_<手机号>`。如果服务端没有做 ACL（**我们无法验证**），任何能连上这个 broker 的人都能订阅别人的推送。
3. **地址不是通用的**：`47.107.37.60` 是洗衣机抓包时的 broker；吹风机实测是 **`39.108.147.136:1883`**。硬编码的值只对前者有效，换学校 / 换设备后很可能连不上（连不上时 `orderNo` 退到 `lastOrder/byMac` 兜底，功能不挂但会慢几秒）。这也意味着想改地址的人还得**同时**把它加进 `network_security_config.xml` 的明文白名单，否则会被系统直接拦掉。

**影响**：泄露的是「谁在什么时候用了多少水 / 买了什么套餐」这类信息，**不含账号密码**。

### 3. 未启用证书固定（Certificate Pinning）

App 没有做证书固定，所以**在设备上安装了自定义 CA 证书的人**可以解密 HTTPS 流量。

**为什么不做**：证书固定会在服务端更换证书时导致**全体用户无法连接**，需要紧急发版；而攻击者也可以反编译去掉固定逻辑。收益与风险不成比例。

**影响**：仅对「已经能在你手机上装证书」的攻击者有效——正常情况下这个人需要先拿到你的设备。

### 4. 密码使用 MD5 处理后传输

趣智校园官方协议要求：`MD5(明文) → 取后 10 位 → 转大写`（`utils/MD5Utils.kt`）。

**MD5 已经不安全**，攻击者拿到摘要后可以暴力枚举。

**为什么改不了**：服务端校验的就是这个格式，客户端改不了。修改密码（`/user/password/update`）、重置密码（`/user/password/forget`）用的也是同一套。

**缓解**：这也是为什么我们**不存密码**——摘要只有在传输中短暂存在。

### 5. App 能发起一卡通代扣（会真的扣钱）

v3.0.1 起支持「请求代扣」（`api/QzxyService.kt` 的 `requestDeduct`，接口是 `POST /order/thirdTrade/single/json/pay`）：如果账单因为余额不足或 12 点后结算失败留在待扣状态，可以在账单上手动补扣。**这是直接操作你校园卡余额的接口，点下去钱就扣了。**（v3.0.2 又修过一批重复扣款隐患，见 CHANGELOG。）

我们做的防护（`ui/MainViewModel.kt` 的 `deductOnce` / `requestDeduct`）：

- 只对**服务端返回的未支付账单**显示按钮，不猜哪些账单该扣
- 点按钮先弹**确认框**，显示金额和笔数
- 结果分**三态**：服务端明确拒绝才叫失败；**请求超时或中断归为「结果未知」**，
  这时不会让你重试，而是重新查一遍服务端状态——因为那笔**可能已经扣成功了**，
  再点一次就是扣两次
- 金额解析不出来时**直接禁用确认按钮**，不让你对着一个可能是假的数字点头
- 同一时刻只允许一笔代扣在途，重复点击会被明确拒掉（不是静默忽略）

> 但说到底，**这是你的钱**。如果不放心，可以只用这个 App 开关水阀，代扣去官方 App 做。

### 6. 蓝牙水表的加解密 / 签名密钥在客户端

v3.1.0 起支持蓝牙水表（手机当网关）。这套协议（凯路设备域）的两把关键材料都以**常量形式写在客户端代码里**，没有放在服务端：

| 位置 | 内容 | 用途 |
|---|---|---|
| `utils/KlcxkjCrypto.kt` | AES-128-ECB 密钥 | 解密服务端下发的 `clData`，再写回设备清掉离线记录 |
| `utils/KlcxkjSigner.kt` | 外层 MD5 固定盐 | 给「下费率 / 上传消费数据 / 上报失败单」三个请求算签名 |

**后果**：APK 是公开的，这两把东西可以被完整提取（它们本来就是从一个 native 库里逆出来的）。提取之后，任何人拿到**自己的一份有效 `loginCode`**（即普通登录一次）就能自己拼签名直接调接口 —— 不需要用我们的 App。

- 影响范围是**设备域**：伪造下费率包、伪造消费数据上报，绕过 App 的所有本地校验。
- 签名里混入了 `loginCode`，所以至少需要攻击者自己先有一个账号，不能凭空签名。
- 这是上游厂商（凯路）的协议设计，**不是我们能在客户端修掉的**——把密钥挪到服务端就等于要自建服务端，那与本项目「没有服务器」的前提冲突。

> 我们只能用代码混淆抬高门槛，抬不高多少。这条就当是公开的：能读到本文的人都能读到密钥。

### 7. 加密存储初始化失败时会退回明文

`utils/PrefsHelper.kt` 里，EncryptedSharedPreferences 初始化失败（设备不支持 / Keystore 损坏）时不会崩，而是**退回明文文件 `linyu_prefs_plain`**，只在日志里留一句警告。

**这意味着第四节第 4 条的「root 之前解不开」在这种设备上不成立**——那份文件是明文的。出现概率不高，但我们不想把这条藏起来。

（回归正轨的做法已经写进代码：两份文件**刻意不同名**，加密恢复后不会去读那份明文，也不会把明文当成加密数据解；那份明文就静静躺着不再被碰，等下次清除数据。）

## 六、历次版本新增的攻击面

按版本分节：v3.1.0 带进来的是套餐计费与 dev 预置凭证，v3.2.1 带进来的是**把凭证写出应用之外**的备份功能。
每一项都改变了风险的量级，和以往的洗澡场景不在一个级别。

### 1. 套餐下单：一次性扣全款，且没有任何退款接口

洗衣机 / 吹风机走的是「按套餐计费」通道（`POST /order/tcpDevice/downRate/modeOrder`），和热水器的「先预扣、按量结算」**完全是两条路**：

| | 按量计费（热水器 / 洗手台 / 饮水机） | 套餐计费（洗衣机 / 吹风机） |
|---|---|---|
| 扣费 | 先预扣，按量结算，多用多扣 | **一次性扣全款** |
| 停止 | `closeOrder` 可以随时停，中途关阀还能结算 | **服务端没有任何停止 / 取消 / 退款接口** |
| 结束 | 用户主动 | 到点由服务端自动关停 |

**为什么这是本轮最需要你知道的：**

- 洗澡点错了还能中途关阀结算，**套餐点错了就是一个套餐的钱，一分不退、也没法叫停**。
- 下单接口成功返回时 `data` 恒为 `null`——**成功的标志就是钱已经扣了**，连 orderNo 都要靠 MQTT 或 `lastOrder/byMac` 事后补。
- 所以「被改包的 App」在这条路径上的后果比洗澡重得多：改包的人可以直接循环调这个接口，一条请求一份钱。

**我们做的防护（App 端）：**

- 选套餐**不扣钱**，必须再点「确认开始」→ 弹 `ConfirmStartDialog` → 才真正发下单请求（`confirmModeOrder` 只做校验 + 弹窗，`commitModeOrder` 才发请求，两步分离）；余额不足、设备被占用、已有进行中的单都在**弹窗之前**就拦掉
- 下单前**先把「可能已扣款」落盘**，再发请求：崩在请求途中也能知道状态，不会让你以为没下过单
- 本地已有进行中的单时**绝不再发**一次——「每发一次就是一份钱」
- 请求抛异常时**不报失败**：超时可能发生在服务端已受理之后，报失败会骗你再点一次 → 第二份钱
- 设备状态查不到时**判「不确定」而不是「空闲」**——站在别人正在用的机器前显示「可使用」，点下去就扣你的钱

> ⚠️ 但这些全是**防误触**，不是防攻击者。改包的人能直接调接口，本地任何确认框都可以被他删掉。这条路径的最终安全边界仍然只有一个：**你装的是哪个包**。

### 2. dev flavor 的预置凭证机制

为了调试免登录，`dev` flavor 支持从 `local.properties` 注入预置登录态（`QZXY_PREFILL_LOGIN_CODE` / `_USER_ID` / `_ACCOUNT_ID` / `_PROJECT_ID` / `_TELEPHONE`）。

设计上有几道明确的闸门：

- **只从 `local.properties` 注入**，该文件在 `.gitignore` 里、不入库；源码里只有占位符，没有真实值。
- **公开构建恒为空串**：`store` flavor 在 `app/build.gradle.kts` 里**显式**写死 `PREFILL_* = ""`，保证原版包永远不含任何凭证。
- **有产物级审计**：`tools/verify_apk.py` 直接扫 APK 的 `.dex` 字节，检查 `loginCode` / 手机号 / `userId` 是否出现在**不该出现**的包里，泄漏即非零退出。**发版前必跑。**
- 已发布的 `v3.1.0-dev` / `v3.2.1-dev` 打包时**临时清空了 `local.properties` 的预置项**，安装后必须自己登录。

**历史踩坑（写出来是因为它会复发）**：`buildConfigField` 曾经写在 `defaultConfig` 里，结果是**所有 flavor 都带上了凭证**——2026-10-24 实测在 `app-store-debug.apk` 的 dex 里真的能搜到 `loginCode`。这种错误编译器不报、单测不报，只能靠扫产物发现。所以这条防线是「机制 + 脚本」，不是「记得别写错」。

> 你自己从源码构建时也要注意：只要 `local.properties` 里还有 `QZXY_PREFILL_*`，打出来的 dev 包就带着**你的**账号。别把自己那份 dev 包发出去。

### 3. 「检查更新」只认 GitHub Release

「检查更新」读的是 `api.github.com/repos/shierpuzi/linyu/releases`，仓库路径是代码里的常量（`api/GithubApi.kt` 的 `REPO_SLUG`）。**不存在任何第三方更新服务器、也没有可被配置替换的更新地址**，所以改包的人除了改代码没有别的办法把你引到他的更新源上。安装前的包名 + 签名一致性校验见第二节。

v3.2.1 起还多了**双通道**（`api/GithubApi.kt` 的 `fetchReleases(devChannel)`）：dev 包只看 pre-release，正式包只看正式版。两个包看到的列表**互不相交**。

> 这不是安全设计，是防误升级：测试版不该把普通用户拉下水，正式版也不该被一个 pre-release 提示「有新版本」。
> 顺带修了个诚实性 bug——以前「网络失败」和「该通道没有版本」都返回空列表，界面一律说「检测失败（多为网络原因）」，
> 明明只是没发版却让人以为网络坏了。现在用 sealed `ReleaseResult` 分开。

### 4. 备份包的安全设计（v3.2.1 新增）
备份功能会**把 loginCode 这类凭证写到应用外面**（用户自己选的位置，可能是网盘），所以它是本轮唯一新增的高风险面。设计如下：

| 项 | 做法 | 为什么 |
|---|---|---|
| 密码派生 | **PBKDF2-HMAC-SHA256，210000 次**，salt 每次随机 16 字节 | 用户密码强度不可控，只能靠慢哈希加成本。21 万次是 OWASP 2023 对 PBKDF2-SHA256 的建议下限；手机上 100~300ms，用户感知不到，暴力破解成本被放大几个数量级 |
| 加密 | **AES-256-GCM**，IV 每次随机 12 字节 | 带认证标签。密码错时解密直接抛异常，不用另存校验位（存校验位反而泄信息给攻击者） |
| 强制加密 | **只要有登录凭证就必须加密**，且这条强制在**数据层**（`BackupCodec.encode` 直接拒绝明文写凭证） | UI 是可以被改坏的（加个分支忘了、勾选状态没同步），而 loginCode 明文落盘是真事故——那文件会被传到网盘、发到群里 |
| 错误分类 | `DecodeError` 分六类（不是备份包 / 结构损坏 / 需要密码 / 密码错 / 空包 / 其他失败） | 否则「选错文件」会被提示成「密码错误」，让人去怀疑自己记错了密码 |
| 文件读取 | 走 **SAF**（系统文件选择器），读前挡 >16MB | 一个存储权限都不要；大文件读进内存会 OOM，而 OOM 是 Error 不是 Exception，**catch 不住** |
| 恢复顺序 | **先鉴权（向服务端验证 loginCode），通过才写本地** | 反过来会出现「点了恢复成功 → 进主页一秒 → 被踢回登录页」 |

**我们能保证的**：附件里的凭证是加密的，且这条路 App 自己关不掉。

**我们保证不了的**：

- **密码忘了打不开，没有任何后门**。这不是留的余地，是设计——有后门就等于这套加密是装饰。
- **备份文件本身可以被拷走、可以被暴力尝试**。21 万次迭代能拖慢攻击者，但挡不住一个弱密码（`123456` 这种）。**请用密码管理器生成一个**。
- 明文备份（只备收藏、且用户没勾加密）是**真明文**。它只含设备收藏，不含账号，这是我们选的默认值；介意就勾上加密。

## 七、你可以做的

### 必做

1. **只从 GitHub Releases 下载**，不要用别人转发的安装包
2. **别信「验签名就能确认正版」这套说法**——正式版现在虽然是 release 签名（见第二节），但签名只证明同源，**真正的判据只有下载渠道**
3. **不要把安装包转发给别人** —— 要分享就发官方链接

### 建议

4. **用系统自带的密码管理器**保存密码，不要用第三方输入法记住
5. **不要 root 手机**，不要安装来源不明的 CA 证书（有些抓包工具要求装证书，装了就给了别人解密你流量的能力）
6. **定期检查「设置 → 应用 → 趣智Lite → 权限」**，正常只需要：蓝牙 / 附近的设备、相机（扫码）、通知、安装未知应用。**不需要通讯录、短信、位置**（定位只在 Android 11 及以下为蓝牙扫描所需申请，Android 12 起完全不申请）
7. **套餐设备（洗衣机 / 吹风机）点「确认开始」前看一眼金额**——那一步之后钱就退不回来了
8. **备份包的密码存进密码管理器**——忘了就真的打不开，没有找回入口
9. 想核对版本来源时，`apksigner verify --print-certs` 对一下第二节那串 SHA-256；对不上先看是不是装了 dev 测试包或旧版本

### 不需要做的

- ❌ 不需要担心「App 偷传数据」——没有服务器可传
- ❌ 不需要定期改密码给这个 App 用——它不存密码
