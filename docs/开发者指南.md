## 一、核心发现：有两条完全独立的控制通道

**客户端控制设备有两条通道，走哪条由「设备联不联网」决定，不是由客户端喜好决定。**

| | 云端通道（`tcpDevice/*`） | 蓝牙通道（`bluetooth/*`） |
|---|---|---|
| 前提 | 设备自带 4G / 已联网 | 设备**不联网**，只能手机当网关（服务端有 `isBle` 字段，但**并非每所学校都下发**） |
| 谁把指令送到设备 | 云端 → 4G → 设备 | **手机通过 BLE 写进设备** |
| 服务端角色 | 直接控制设备 | 只下发**费率包** + 记账，阀由手机开 |
| 断连后果 | 云端能兜底 | **设备可能停在「开了但没记账」**，必须主动上报失败 |
| 典型接口 | `/order/tcpDevice/downRate/rateOrder`、`closeOrder` | `/order/downRate/bluetooth/rateOrder`、`/order/upload/bluetooth/data`、`/order/upload/bluetooth/fail` |
| 本项目实现 | `data/ShowerController.kt` | `data/BleShowerController.kt` + `ble/BleController.kt` |

```
云端通道:
  手机 → HTTP (https://v3-api.china-qzxy.cn) → 云端 → 4G → 热水表
  手机 ← MQTT (明文 1883) ← 订单/消费推送

蓝牙通道:
  手机 ⇄ BLE GATT (服务 FF00 / 通知 FF01 / 写 FF02) ⇄ 水表
  手机 → HTTP → 云端（只为了要费率包、上传消费、上报失败）
```

两条通道**不能混用**：对一台只支持蓝牙的水表调 `tcpDevice` 接口，服务端必然返回
`errorCode=306 设备不在线`——它不是网络问题，是这台设备压根没联网。

> 更麻烦的是：**服务端并不总是下发「这台是不是蓝牙表」的字段**。本项目实测某校时，
> `/device/info/mac` 的响应里 `isBle` 一次都没出现过。所以客户端的做法是
> ① 云端开阀吃到 306 时弹框问用户「要用手机蓝牙方式开启吗」，
> ② 用户确认后把这个 `snCode` 记进本地白名单，以后直接走蓝牙。
> 详见第五节「BLE 扫描与蓝牙水表」。

## 二、认证体系

### 基础信息

| 项 | 值 |
|---|---|
| Base URL | `https://v3-api.china-qzxy.cn` |
| 数据格式 | JSON；GET 参数在 URL，POST 为 `application/x-www-form-urlencoded`（**唯一例外**：`/order/thirdTrade/single/json/pay` 用 JSON body） |
| 认证方式 | `loginCode` 会话认证 |

### 登录

```
POST /user/login
Body: telephone=手机号&password=加密密码&phoneSystem=android&type=0&version=6.5.28
```

密码算法：**MD5(明文) → 取末尾 10 字符 → 转大写**

返回：

```json
{
  "success": true,
  "data": {
    "userId": 10000001,
    "loginCode": "32 位小写 hex",
    "userAccount": {
      "accountId": 15384,
      "name": "用户名",
      "projectId": 3356,
      "accountRealMoney": 26.14
    }
  }
}
```

`userAccount` 是**单项目**视角：它给的是「当前这条绑定关系」的 `accountId` + `projectId`。
账号若绑了多个项目，其余项目要再调 `/user/project/list` 拿（见第四节）。

### 三种登录方式

| 方式 | 接口 | 需要的输入 |
|---|---|---|
| 密码登录 | `POST /user/login` | 手机号 + 密码（MD5 取后 10 位大写） |
| 验证码登录（默认） | `POST /user/registerAndLogin` | 手机号 + 短信验证码，**未注册自动建号** |
| loginCode 登录 | 无（直接复用已有会话） | **`loginCode` + `userId`** |

`loginCode` 登录必须两个字段一起给：只传 `loginCode` 时所有接口都返回
`errorCode=8 未获取到用户信息`，而 `loginCode` 是 32 位随机 hex，**反推不出 `userId`**。
拿到这两个之后其余参数由程序自己解析：

```
loginCode + userId
  → GET /user/project/list   → accountId + projectId（同时验证 loginCode 有效）
  → GET /account/info        → telephone / name / 学号
```

⚠️ **必须「先校验再落盘」**：这两步里任何一步失败都不许写本地存储。普通登录的响应
一次给齐 5 个参数，失败就是失败；而 loginCode 登录是分步凑参数的，
中途写盘会让用户进入「能进主界面、但每个请求都返回 `errorCode=8`」的半登录状态——
比直接报错难查得多，而且他还得先退出登录才能重试。

⚠️ **挤号是双向的**：这枚令牌在原 App 里依然有效。你用它登录，原 App 立刻掉线；
原 App 再登录一次，你也掉。同一枚令牌不可能两处同时在线。令牌失效表现为
`errorCode=8`，但 **HTTP 仍然是 200**。

App 已登录时**从任意业务请求的 URL 里**就能抠出全套参数，不用重新登录、不会挤掉正在用的 App
（只是「看」不占会话，一旦拿去「用」才会挤）。

### 全局认证参数

所有请求需携带（GET 放 URL 参数，POST 放 Body）：

```
loginCode={token}&userId={uid}&accountId={aid}&projectId={pid}
&telephone={phone}&telPhone={phone}&phoneSystem=android&version=6.5.28
```

**除参数外还要带两个请求头**（官方 v3 API 的固定要求，缺了结算类接口会报
`226 加密校验失败`）：

```
Config-Project: {projectId}
Config-Keys:    module_list,advertise_type,question_list,service_phone_list,
                banner_list_app,activity_list_app,aliCard_popup_config
```

`loginCode` 有效期长，可持久化到本地存储（本项目用 `EncryptedSharedPreferences`）。
**但它是单点的**：任何一处登录，其余立即失效；官方 App / 第三方客户端会互相挤。

### 短信 secret 算法

`/user/verification/code/get` 需要一个 `secret` 参数。抓包时代看上去像是每台设备各不相同的随机值，
实际上它**完全由手机号推导**：

```
secret = MD5( 手机号前3位 + 手机号后4位 + "klcx" )
```

以 `13800138000` 为例：`MD5("138" + "8000" + "klcx")` = `f000554d9cb90c44bd0ae2ded9a847aa`。

因为不含任何设备侧密钥，**任何手机号都能在本地算出自己的 secret**，所以短信验证码登录可以
通用实现，无需抓包。

> 结论：secret 不是身份凭据，真正的身份校验发生在 `/user/registerAndLogin` 提交验证码那一步。

## 三、核心 API

`QzxyService.kt` 里一共有 **35 个接口**，下面按用途分组全量列出。字段含义以实际样本为准；
标「未采到样本」的，只保证接口路径与参数，**响应体不要照着猜**。

### 3.1 登录与账号

| 功能 | 方法 | 路径 | 说明 |
|---|---|---|---|
| 登录 | POST | `/user/login` | MD5 密码，`version=6.5.28` |
| 短信验证码登录 / 注册 | POST | `/user/registerAndLogin` | `telephone` + `smsCode`，`type=5` |
| 发送短信验证码 | GET | `/user/verification/code/get` | 需 `secret`（见第二节）、`typeId` 决定用途、`platform=1` |

| 已绑卡信息 | GET | `/account/card/getBindCardInfo` | `/account/info` 的**超集**（源码注释称多出 `lastConsumeTime` / `useCount` / `cardCost`）。存在的意义是兜底：`/account/info` 的 `name` 要学校把学籍同步过来才有，没同步就是 `null`，两个接口数据来源不同，一个没有另一个可能有。⚠️ 完整响应**未采到样本**，字段按代码模型列出，别当已验证 |

```json

### 最容易踩的五个坑

**1. 接口失败也返回 HTTP 200。** 错误全在 body 的 `success` / `errorCode` / `errorMessage` 里。
判断成功一律看 `success`（有的接口连 `success=true` 都可能带错误码，见第 5 条），别看状态码。

**2. GET 请求也要带 `telPhone`。** 绝大多数接口只认 `telephone`，但
`/settlement/campus/userInfo` 偏偏要 `telPhone`，少传就返回
`errorCode=1 手机号不能为空`（HTTP 依然是 200）。两个都带上最省事。

**3. 验证码 `typeId` 用错就收不到码**（对照表见 3.1）。

**4. `/order/tcpDevice/closeOrder/result/query` 确认不了任何东西。**
它的 `data` **恒为 `null`**。用它判断「关阀成功」的写法（`d == null || d.state == 0 || ...`）
会**第一轮就跳出循环**——那段「确认」实际只验证了「HTTP 请求成功」，跟设备关没关无关。

**想知道设备到底关没关，只能问 `/order/tcpDevice/query/rateOrder/using`**：
服务端说这台上没有订单了，才是真停了。而且判据必须写成**三态**
（有订单 / 明确没有 / 请求失败不确定），写成 `Boolean` 就必然把「不知道」当成「关好了」。

**5. `success=true` 不等于没出错。** 套餐设备的 `washer/status` 在**设备被占用**时
返回的就是 `{"success":true,"errorCode":307,"errorMessage":"设备正在使用中",...}`。
只判 `success` 会以为查询成功、然后拿 `data != null` 去猜；必须显式判 `errorCode`。

**各接口的完整请求/响应示例见 [API-qzxy.md](API-qzxy.md)。**

### 开始洗澡完整流程（云端通道）

1. BLE 扫描 → 发现 `KLCXKJ-Water` → 获取 MAC 地址
2. `GET /device/info/mac` → 获取 `snCode`、`deviceName`、`withholdMoney`
3. 连接 MQTT `tcp://47.107.37.60:1883`（无认证；地址可能因校而异，见第十节）
4. `POST /order/tcpDevice/downRate/rateOrder` (`xfModel=0&snCode=xxx`)
5. `POST /order/tcpDevice/query/downRateResult` 轮询确认开阀 —— **响应里直接带 `orderNo`**，
   **不用等 MQTT，也不用再轮询 `queryUsing`**。确认前该接口会返回
   `errorCode=1 网络通讯慢,请稍后再试`，继续轮询即可
6. 已开阀时是 `state=1, result=0` —— **`state` 不是 0**，判断要两个都看
7. 落盘：开阀时间戳、活跃订单、`autoDisConTime`（自动关停秒数）

### 停止洗澡

`POST /order/tcpDevice/closeOrder` (`snCode=xxx&orderNo=xxx`)

⚠️ **关阀的「确认」要另想办法**：`/closeOrder/result/query` 的 `data` 恒为 `null`，
拿它判断等于没判断。要靠 `queryUsing` 是否还有订单来确认——见上面第 4 条坑。

### 恢复进行中的订单

`POST /order/tcpDevice/query/rateOrder/using` + `snCode`。如果 `errorCode=307`，
`data.orderNo` 即当前订单号，调用 `closeOrder` 停止。
**注意**：`data.isOwner=true` 说明订单属于当前账号，`false` 说明别人在使用——别把别人的单当自己的恢复。

## 四、多项目（板块）通道

### 一个手机号可能绑多个**独立项目**

实测某校（同一手机号、同一个 `userId`）：

| 板块 | `projectId` | `accountId` | 业务 | 计费 |
|---|---|---|---|---|
| 洗浴 | **4000** | 3987 | 热水表 | 按量计费 |
| 洗衣饮水吹风 | **3356** | 15384 | 洗烘 / 饮水 / 吹风机 | **按套餐一次性扣全款** |

两个项目**钱包独立、账单独立、设备独立**，界面上就是官方 App 首页那两个板块。

`GET /user/project/list` 的实际响应 `data`：

```json
[{"userId":10000001, "projectId":3356, "accountId":15384},
 {"userId":10000001, "projectId":4000, "accountId":3987}]
```

`UserProject` 只有三个字段，**全部可空**：

| 字段 | 说明 |
|---|---|
| `userId` | 全局一个，两个项目相同 |
| `projectId` | 项目 id |
| `accountId` | **服务端为每条绑定关系单独分配的**，不同项目不同。具体值运行时读，别硬编码 |

### ⚠️ `projectId` 与 `accountId` 必须成对切换

`loginCode` + `userId` 是**全局一套**（一个账号一套），但换 `projectId` 时必须**同时**换
`accountId`。只换 projectId，服务端回 `「没有项目权限，请确认身份」`——
而且这种错误在界面上只表现为「数据是空的」，非常难查。

实测证据（同一个 `loginCode`，只换上下文）：

| 上下文 | `/account/info` 返回 `projectId` | `accountId` | `userId` |
|---|---|---|---|
| `projectId=3356&accountId=15384` | 3356 | 15384 | 10000001 |
| `projectId=4000&accountId=3987` | 4000 | 3987 | 10000001 |

同一套 `loginCode` 能操作两个项目，**前提是 accountId 配对正确**。

### 当前项目启用了哪些业务模块

`GET /project/module/list`（用 3356 的上下文调）返回 8 个模块，**只有 3 个启用**：

| `moduleId` | `moduleName` | `isUse` |
|---|---|---|
| 3 | 洗烘 | **1** |
| 4 | 饮水 | **1** |
| 5 | 吹风机 | **1** |
| 1 | 公寓洗澡 | 0 |
| 2 | 澡堂洗澡 | 0 |
| 6 | 无线澡堂 | 0 |
| 7 | 充电 | 0 |
| 8 | 远传水电表 | 0 |

官方 App 首页那排图标就是按它渲染的，`isUse == 1` 才显示。

`ProjectModule` 字段：

| 字段 | 说明 |
|---|---|
| `moduleId` / `projectId` / `moduleName` | 模块标识与名字 |
| `isUse` | `1` = 启用；`0` 或其它 = 不启用 |
| `openUseParagraph` / `restraintType` / `restraintContext` | 使用时段与限制说明，本项目未用到 |
| `bigTypeIds` | 模块对应的大类 id 列表，**服务端目前不填（实测为 null），别依赖它** |
| `moduleKey` | 模块键 |

### 踩坑清单

1. **`/project/module/list` 用 4000 调会报「没有项目权限，请确认身份」**——
   即使账号明明绑了 4000 的账户也一样。所以**不能靠它判断某个板块有哪些业务**。
   要知道「这个学校有没有洗衣机业务」，只能用当前能调通的板块（3356）的模块列表，
   或者直接看设备台账里的 `bigTypeId`。
2. **切换板块前必须确认没有进行中的订单。** 在途订单是用旧 `accountId` 开的，
   切走之后关阀/结算都会失败。
3. **切换后要清项目维度的缓存**，否则切过去先显示上一个板块的账单/余额。
4. **设备页的余额要用「设备自己所属的板块」**，不是「当前板块」：
   `/device/info/mac` 会原样下发设备的 `projectId` / `projectName`，且不受请求上下文影响。
   用错就是「洗浴页显示洗衣板块的钱」。
5. **想只读借用另一个板块的参数，必读这段**：本项目的认证参数是 `NetworkModule` 里的
   **全局可变状态**，所有请求共用。借另一个板块的参数跑查询时，**其他并发请求会带错参数**。
   缓解办法只有：同一时刻只允许一个借用任务、借用期间只发 GET、用完立刻还原
   （本项目叫 `withBoardContext`，用 `finally` 保证还原，且不改落盘、不清缓存）。
   这是这套架构的固有缺陷，新写客户端建议直接给每个板块一套独立 client。

### 登录后选哪个板块

优先级：**用户上次选的那个** → 登录响应里的 `userAccount.projectId` → 列表第一个。
老用户升级后没有「上次选择」，于是直接沿用登录响应那个，不产生任何可见变化。

## 五、BLE 扫描与蓝牙水表

### 5.1 扫描（只用来发现设备）

| 项 | 值 |
|---|---|
| 广播名 | `KLCXKJ-Water`（过滤时 `ignoreCase`，软件过滤，不依赖硬件 ScanFilter） |
| 常见 MAC 前缀 | `C4:7F:0E`（**只是常见值，不做过滤依据**） |
| 厂商 | 凯路创新科技 |
| 扫描时长 | 5 秒足够 |

扫到之后拿 MAC 去 `GET /device/info/mac` 换 `snCode`。对**云端通道**的设备，到这一步就够了，
不需要连 GATT。对**蓝牙水表**，这才刚开始。

### 5.2 广播地址 ≠ 台账 MAC（两个方向相反）

`/device/info/mac` 是拿 MAC 当**字符串**查台账的，而手机扫到的地址与台账里存的**不是同一个**。
实测（projectId=71）：

| 来源 | 值 | 拿去查 `/device/info/mac` |
|---|---|---|
| 安卓 `BluetoothDevice.getAddress()`（空口广播地址） | `C0:15:83:04:D3:00` | `{"success":true,"data":null}` |
| 服务端台账的 `macAddress` | `00:15:83:04:D3:00` | 完整设备信息 |

原因是蓝牙规范要求**随机静态地址的首字节最高两位必须是 1**，设备据真实 MAC 派生出广播地址。
所以两个方向各要一次换算：

| 用途 | 换算 |
|---|---|
| 查台账 | 广播地址 → 台账 MAC（清掉首字节最高两位） |
| 连蓝牙 | 台账 MAC → 广播地址（置上首字节最高两位） |

两个方向都只是**首字节最高两位**的差异。是否命中要看学校：台账里存的就是广播地址的学校
（`C4:7F:0E` 那类）第一次就命中，不会有额外请求。

⚠️ 这不是万能公式：设备若用**完全随机**的静态地址或私有地址（RPA / NRPA），两个地址毫无关系，
换算必然失败。本类只用来**增加候选**，原样地址永远排第一，命中不了就继续往下试。

### 5.3 GATT 连接

| UUID | 用途 |
|---|---|
| `0000FF00-0000-1000-8000-00805F9B34FB` | 水控服务 |
| `0000FF01-...` | 通知（设备应答走这里） |
| `0000FF02-...` | 写入（命令走这里） |
| `00002902-...` | CCCD，必须写 `ENABLE_NOTIFICATION` |

要点：

- **必须等到「通知开启」成功之后才能发命令**。刚 `connected` 就写，特征还没拿到，
  `writeCharacteristic` 返回 false 且很容易被忽略。
- **写入要分片**：BLE 单次写入上限是 MTU-3（默认 20 字节），一帧 HEX 文本动辄上百字节。
  本项目按 20 字节分片、**逐片等回执**、片间隔 20ms。
- **发命令前先清残留帧**。设备会主动推上一笔未结算交易的 `0x22`+`0x85`
  （官方「蓝牙重连自动结算」的设备侧机制），不清就会把旧消费数据当成本次命令的应答。
- 连上了但**找不到 FF00/FF01/FF02** → 说明这台**根本不是**水控设备，应撤销「需要蓝牙」的标记；
  这和普通连接失败（超时/走远了）不是一回事，后者的标记要保留。

### 5.4 帧格式（`ble/BleFrame.kt`）

二进制帧：

```
下标:  0     1     2        3     4     5      6 … 6+n-1   6+n    7+n
含义: 0x60  0x00  len+3   0x80  cmd   0x00   data[…]     crc   0x16
```

- `len = data.size + 3`（下标 3、4、5 三个字节算进长度）
- `crc = (sum(data) + 0x80 + cmd) % 256`
- 总长 = `data.size + 8`

线上帧（真正写进 BLE 特征的字节）：

```
0x23('#') + 二进制帧的大写 HEX 文本(ASCII) + 0x0A('\n')
```

⚠️ 发的是 **HEX 文本**而不是原始二进制——写错的后果不是报错，是设备**静默不理你**。

命令字：

| cmd | 用途 | 应答成功标记 |
|---|---|---|
| `0x23` | 查询状态 | payload 首字节 `0x80` |
| `0x21` | 下发费率包（**真正开阀**） | `payload[0] == 0x80` |
| `0x22` | 关阀（传一个零字节，不是空载荷） | `payload[0] == 0x80` |
| `0x85` | 采集消费数据（传一个零字节） | payload 即 `xfData` |
| `0x86` | 写回设备存储（清设备侧记录） | `payload[0] == 0x80` |

### 5.5 状态帧的下标随长度而变

`0x23` 的应答载荷**有两套布局**，按长度分支，其余长度一律报「未知」——宁可报错也不要拿错的偏移去读，
那会把错误的 `macType` 发给服务端：

| 载荷长度 | `protocolType` | `randomNumber` | `state` | `devType` / `a1` |
|---|---|---|---|---|
| **28 字节**（短布局） | 无此字段，给空串 | `p[21..22]`（4 位 hex） | `p[19]` | `p[23]` / `p[24]` |
| **≥31 字节**（长布局） | `p[19]` | `p[24..27]`（8 位 hex） | `p[28]` | `p[29]` / `p[30]` |

`state` 的已观测值：`0` 空闲、`1` 使用中、`3` 消费已结束数据待采集、
`6` 已关阀但有遗留未结算记录。`3` / `6` 都要走一次「补结算」才能恢复空闲，否则下次仍然开不了阀。

### 5.6 签名与加解密

**签名**（`utils/KlcxkjSigner.kt`，纯 Kotlin，已用 12 组样本交叉验证）：

```
内层 = MD5( raw + "&key=" + sessionKey )
签名 = MD5( 内层 + "&key=sign-kailu-855c74a88b8b494187c99b08b8c9a744" )
```

- `raw` = 参与签名的字段按 **key 字典序升序** 拼成 `key1value1key2value2…`（无分隔符；
  value 为 null 时**整个字段跳过**，不是当空串）
- `sessionKey` = 服务端下发的 `loginCode`
- 外层那串是**固定常量**，且自带 `&key=` 前缀，这不是笔误

⚠️ **各接口参与签名的字段不一样**，写错就被判签名无效：

| 接口 | 参与签名的字段 |
|---|---|
| `bluetooth/rateOrder` | `telephone`、`deviceId`、`xfModel`、`randomNumber` |
| `upload/bluetooth/data` | `loginCode`、`telephone`、`xfData` |
| `upload/bluetooth/fail` | `consumeDate`、`loginCode`、`telephone` |

`randomNumber` **必须用设备状态帧里给的值**，本地生成的对不上；`xfData` 参与签名与上传
**必须都是小写**（大小写不一致会得到 `170 签名错误`，这是排查了很久才定案的根因）。

**加解密**（`utils/KlcxkjCrypto.kt`）：AES-128-ECB，密钥 `20210118klcx@002`，
密文是标准 Base64，加密填充 PKCS#7，解密兼容 PKCS#7 与零填充。
它只用来解服务端返回的 `clData` → 拿 `-` 之后那段 → `0x86` 写回设备。

> 缺了这一步，设备侧离线记录清不掉，会停在 `state=3`，**下次开阀报「设备正在使用中」**。
> 早期版本把这步当「可选」降级成恒 null，结果设备卡死无法再开阀。

### 5.7 开阀 / 结算流程（`data/BleShowerController.kt`）

```
开阀：连接 → 查询状态(0x23) → 下费率(HTTP bluetooth/rateOrder) → 写费率包(0x21) → 等 ACK
结算：关阀(0x22) → 断开重连 → 查询状态 → 采集(0x85) → 上传(HTTP upload/bluetooth/data)
      → 解密 clData → 写回(0x86) → 清设备记录
```

三个必须守住的点：

1. **费率包必须来自服务端**——自己造一个写进设备，可能多扣钱或损坏设备
2. **`randomNumber` 必须用设备给的**（在状态帧里）
3. **失败必须上报** `upload/bluetooth/fail`——蓝牙通道没有服务端兜底，不报的话这一单会一直
   挂在预扣状态

其它实测细节：

- **关阀后必须断开重连再采集**。同一连接里「关阀后立刻采集」的数据会被服务端判
  `226 加密校验失败`（账单停在 0.0）；重新连接后采集的数据能被接受。
  代价是关阀多 1~2 秒。
- **补结算完成后要用户重新点一次开阀**：设备不会立即为下一个订单生成新的 `randomNumber`
  （只有 `rateOrder` 时才更新），立刻开阀会复用旧 random 被判签名错。
- **恢复用水**：开着水时 App 被杀，重开通过设备 `state != 0` + 本地有该设备的活跃订单，
  判定为「自己上一次没关干净」，沿用当前会话进使用页，不重新开阀。
- 上传接口把 `errorCode` **0 / 206 / 209 都算成功**（服务端历史遗留，不同学校口径不一）。

### 5.8 用 tcpDevice 调这类设备会回 306

`errorCode=306 设备不在线` = 云端到不了这台设备。它不是网络问题，**大概率就是台蓝牙表**。
但服务端并不总给 `isBle` 字段，所以客户端只能：

1. 云端开阀吃到 306 → 弹框问用户「要用蓝牙方式开启吗」（并说明开启时必须待在设备旁边）
2. 用户确认 → 走蓝牙通道，成功后把 `snCode` 记进本地白名单（记 `snCode` 不记名字/MAC：
   名字各校不同，MAC 有虚拟/真实之分，`snCode` 才是开阀接口真正用的标识）
3. 蓝牙连上但找不到 FF00 服务 → 说明当初猜错了，自动撤销白名单

## 六、按套餐计费的设备（洗衣机 / 吹风机）

### 6.1 先分流：按「计费模型」，不按设备类型

判据**只有数字**（`bigTypeId` / `smallTypeId`）。服务端对同一个 `bigTypeId=6` 在三处接口里
叫「洗衣机 / 洗烘设备 / 洗烘设备」，**名字不能用来分支**。

| 设备 | `bigTypeId` | `smallTypeId` |
|---|---|---|
| 洗衣机 | **6** | **3** |
| 吹风机 | **7** | **5** |
| 热水表 | 4（或 1） | 1 |
| 饮水机 | 5 | — |

`smallTypeId` 只在 `bigTypeId` 缺失时用作**兜底**（它是弱判据：历史上 `smallTypeId=1`
被当成蓝牙特征，导致整个学校的 4G 表都开不了阀）。有 `bigTypeId` 时一律以它为准。

| | 按量计费 `METERED` | 套餐计费 `PACKAGE` |
|---|---|---|
| 哪些设备 | 热水表 / 洗手台 / **饮水机** | 洗衣机（6/3）/ 吹风机（7/5） |
| 下单 | `downRate/rateOrder`（`xfModel=0`） | `downRate/modeOrder`（`xfModel=`套餐 `modeId`）|
| 扣费 | 先预扣、按量结算 | **一次性扣全款，不可退** |
| 中途停止 | `closeOrder` 可以停 | **没有任何停止/取消/退款接口** |
| 时长 | 用到多久算多久（`autoDisConTime` 是上限） | 固定，**服务端到点自动关停** |
| `orderNo` | `downRateResult` 直接给 | 只能从 MQTT / `lastOrder/byMac` / `bill/detail` 取 |
| 状态查询 | `query/rateOrder/using`（可靠） | `washer/status`（空闲 `data:null`，占用 `errorCode=307`）|
| 结算 | `consumeOrder/result/query` | 无（扣款即全额） |
| 界面 | 已用时长 + 「结束使用」按钮 | 选套餐 + 剩余倒计时，**没有停止按钮** |
| 蓝牙表 | 同按量，只是控制走 BLE | — |

> ⚠️ **饮水机在洗衣饮水吹风项目里，但计费是按量**。账单实测：饮水机
> `preDeduct=2.0` 而 `consumeMoney=0.1/0.44`（**不等**）；洗衣/吹风是
> `preDeduct == consumeMoney`（相等）。**别把饮水机并进套餐通道**——那会做出一个
> 「饮水机也显示到点自动结束」的界面，而它其实是预扣 2 元后按量结算。

### 6.2 `rateOrder` 与 `modeOrder` 是两条完全不同的路

| | `tcpDevice/downRate/rateOrder` | `tcpDevice/downRate/modeOrder` |
|---|---|---|
| `xfModel` | 固定 `0` | **套餐的 `modeId`**（不是 `id`） |
| 扣款方式 | 预扣，按用量结算 | **一发出就扣套餐全款** |
| 响应 `data` | 有 `orderNo` / `autoDisConTime` / `state` / `result` | **恒为 `null`** |
| 成功判据 | `downRateResult` 确认 `state=1,result=0` | 只有 `success=true` |
| 停止 | `closeOrder` | 无 |
| 结束 | 用户主动 / 到 `autoDisConTime` | 服务端到点自动关停，**不通知客户端** |

`modeOrder` 请求（实测通过）：

```
POST /order/tcpDevice/downRate/modeOrder
xfModel=29&snCode=C47F0E2351BE&isHaier=0
&accountId=15384&projectId=3356&userId=10000001&loginCode=...&telephone=...&version=6.5.28
→ {"success":true,"errorCode":0,"data":null}
```

它**一发出就扣钱**，而服务端**没有任何** stop / close / cancel / refund 接口（洗衣机、吹风机
两次完整抓包都证实了）。所以调用方必须自己承担三件事：

1. **二次确认 UI**：点下单前让用户看清「X 元 / N 分钟」，并明确告知「立即扣款、不可退款、
   到点自动结束」。不要做成「点一下就开始」。
2. **防重复点击**：本地「已有进行中的单」只能挡住一部分，**挡不住双击造成的两次并发请求**，
   UI 必须自己置灰按钮。
3. **文案不写「停止」**：没有这个功能，写「到点自动结束」。

### 6.3 套餐列表与单位

`GET /device/mode/list?smallTypeId=5`（吹风机实测）：

| `modeId` | `modeName` | `modeMoney`（厘） | 折算 | `modeTimeMinute`（字符串） | `modeTimeQuantity`（秒） | 抓包里选中 |
|---|---|---|---|---|---|---|
| 29 | 电吹风模式一 | 600 | 0.6 元 | `"3"` | 180 | ✅ |
| 30 | 电吹风模式二 | 1000 | 1.0 元 | `"5"` | 300 | `isSelected=1`（默认高亮） |
| 31 | 电吹风模式三 | 2000 | 2.0 元 | `"10"` | 600 | |

洗衣机（`smallTypeId=3`）：33 标准洗 4 元/35 分、34 快速洗 3 元/25 分、
35 单脱水 1 元/10 分、36 大件洗 5 元/45 分。

**单位混乱，务必看清**：

| 字段 | 单位 |
|---|---|
| `modeMoney` | **厘**（1000 厘 = 1 元） |
| `modeMoneyYuan` | 元（Double） |
| `modeTimeMinute` | **字符串**分钟 |
| `modeTimeQuantity` | 秒 |

换算用 `MoneyFormat.milliToYuan()`，别自己写 `/1000.0`（那正是差 1000 倍的经典坑）。
价格拿不到时显示占位符，**不能显示成 `0.00`**——「免费」和「不知道多少钱」是两件事。

### 6.4 `orderNo` 只有三条路，首选 MQTT

`modeOrder` 的响应里没有单号，而后续对账、通知、账单展示都要它。

**① MQTT `app_downRate_{手机号}`（最快，实测几十毫秒）**

吹风机抓包原文：

```json
{"xfModelName":"电吹风模式一", "orderNo":"13202610240012244626",
 "preDeductMoney":600, "deviceSnCode":"C47F0E2351BE",
 "consumeDate":"20261024001224", "state":1, "result":0,
 "consumeSceneType":4, "accountId":15384, ...}
```

⚠️ **热水器的 `rateOrder` 单号也发在同一个 topic 上**，必须过滤，否则会把水单的单号记到洗衣机头上。
过滤按可靠性排序：

1. 推送里有 `deviceSnCode` → 必须等于本机 pending 的 `snCode`（服务端给的设备标识最可信）
2. 没有 `deviceSnCode` → 退到 `consumeSceneType == 4`（**只有一个吹风机样本**，弱判据）
3. 都判不了 → **丢弃**，让 ② 兜底。记错单号比暂时没有单号更糟

⚠️ `MqttManager` 里 broker 是硬编码的，而实测 broker 换过（见第十节）。连不上就一条推送都收不到，
所以 ② 是必备兜底。

**② `GET /order/query/lastOrder/byMac`（免费，开发期神器）**

```json
{"orderId":11868418, "orderNo":"13202610240012244626",
 "deviceId":1252, "smallTypeId":5, "macAddress":"C47F0E2351BE",
 "preDeductMoney":600, "xfModel":29, "modeName":"电吹风模式一",
 "modeMoney":600, "modeTime":180,
 "consumeDate":"2026-10-24 00:12:24", "deviceName":"吹风机-..."}
```

`data` 是**扁平对象**（不套包装）。`orderId` 是账单序号，和 `orderNo` 不是一回事。

⚠️ **有时间窗口**，实测：

| 查询 | 结果 |
|---|---|
| 1 小时前的单 | ✅ 有数据 |
| 19 天前的单 | ❌ `data:null` |
| 不存在的 MAC（`FFFFFFFFFFFF`） | ❌ 同样的 `data:null`（不做错误区分） |
| 跨项目（用 4000 上下文查 3356 的车） | ❌ `null`，正常 |

所以**不能拿 `data == null` 判「这台设备没人用过 / 设备空闲」**。
而且它返回的是该设备**最近一单**，不比对就会把半小时前那单的单号贴到这次消费上。必须核两件事：

- `xfModel` 对不对得上本次选的 `modeId`（同一台设备换档是常态）
- `consumeDate`（转毫秒后）不能比下单时刻早太多（留 5 分钟容差，覆盖手机与服务端的时钟偏差）

**③ `GET /order/query/account/bill/detail?consumeDate=`（无窗口，但本项目未接入）**

账单详情按 `consumeDate` 定位，理论上没有 byMac 那种时间窗口，是更稳的兜底。
代价是**手机时钟与服务端时钟差几十秒就可能查不到**，要做 ±2 分钟的试探查询。
本项目评估后没接（属于待办），只用 ①②。

### 6.5 `washer/status` 的三态与占用态样本

| 情况 | `success` | `errorCode` | `data` |
|---|---|---|---|
| 空闲 | true | 0 | **null** |
| 被**别人**占用 | **true** | **307** | 非空 |
| 自己的单占用 | true | ? | 非空（**未采到样本**） |
| 请求失败 | — | — | 必须判为「不知道」 |

2026-10-24 09:51 实测的占用态原文（洗衣机被别人用着）：

```json
{"success":true,"errorCode":307,"errorMessage":"设备正在使用中",
 "data":{"expireTimes":729,"orderNo":null,"isOwner":false,
         "accountId":null, "modeMoney":null, "modeTime":null, ...其余全是 null}}
```

四个关键事实：

1. **`success` 仍然是 `true`**——只看 success 会误判，必须显式判 `errorCode == 307`
2. **`data.orderNo` 是 `null`**：那不是你的单，服务端不给你别人的单号，别指望从这里取 `orderNo`
3. **`expireTimes` 是剩余秒数**：随后三轮依次 729 → 649 → 589，逐轮递减约 60 秒（轮询间隔 20s × 3 轮）
4. `isOwner` 别人占用时为 `false`

交叉验证：同期 `lastOrder/byMac` 那单是「快速洗 25 分钟」、09:38:39 下单，
`09:38:39 + 25min = 10:03:39`；而 `09:51:32` 的 `expireTimes=729s` → `10:03:41`，**吻合到 2 秒**。

⚠️ **名字叫 washer 但吹风机也调这个接口**，不是洗衣机专用。
⚠️ **判据必须三态**：`307 || (success && data != null)` → 占用；`success && data == null` → 空闲；
**其它一律「不知道」**。断网时把「不知道」当「空闲」，会让用户站在一台别人正在用的机器前
看到「可使用」，点下去就扣他的钱。

**未采到样本**：`modeOrder` 的失败响应（余额不足 / 设备离线 / 无权限长什么样）；
`washer/status` 在「自己的单占用中」时的完整返回。

### 6.6 下单结果必须三态，不能只有成功/失败

| 结果 | 含义 | 界面处理 |
|---|---|---|
| `Placed(orderNo)` | 已下单且拿到单号 | 进使用页 |
| `Failed(msg, errorCode)` | **钱没花出去**（服务端明确拒绝，`success=false`） | 可让用户重试 |
| `AwaitingOrderNo` | **钱很可能已经扣了，但 `orderNo` 还没拿到** | 显示「已开始，正在获取订单信息」，允许稍后重试 |

第三条是关键：`modeOrder` 一发出就扣全款、不可退、没有取消接口。
**谎报失败会让用户再点一次，于是扣第二份钱**。请求超时抛异常时同样**不知道钱扣没扣**，
也只能归到 `AwaitingOrderNo`。实现上要「**先落盘 pending 再发请求**」——
崩在请求途中也能知道「可能已经扣钱了」。

### 6.7 倒计时是本地的

抓包证明下单后 180 秒内 App **一个业务请求都没发**：服务端没有「结束」事件可等，
倒计时只能客户端自己算。

- 起点用**下单那一刻的本机时间戳**，时长用 `modeTimeQuantity`
- 判「结束」要留余量：实测 0.6 元/3 分钟那单，下单 00:12:24 → 账单结束 00:15:25，
  共 **181 秒**。早一秒钟宣布「已结束」，用户看到的可能还是转着的机器，所以
  「大概率结束」= 已过时长 ≥ `modeSeconds + 5`
- 手机时间被改 / 时钟回拨时，剩余时间按**整段时长**算（当作刚开始），别按负数或 0
- 倒计时到点只表示「大概率结束了」，想确认只能再查一次接口

## 八、一卡通余额

**能直接调用。不用去碰易校园。**

趣智校园把易校园的接口代理了：

```
GET /settlement/campus/userInfo
    ?projectId={项目}&telPhone={手机号}&userId={用户}&accountId={账户}&telephone={手机号}&...
```

```json
{"success": true, "data": {
  "studentNumber": "202400000000000",
  "studentName": "张三",
  "amount": "16.76",
  "signStatus": 1
}}
```

| 字段 | 说明 |
|---|---|
| `amount` | **一卡通余额，字符串**（要自己转 Double） |
| `signStatus` | `1` = 已签约免密支付，`0` = 未签约 |
| `studentNumber` / `studentName` | 学号 / 姓名，和 `/account/info` 一致 |

### 两个坑

**① 这个接口出错也返回 HTTP 200。** 错误在 body 的 `success` / `errorCode` 里：

```json
{"success": false, "errorCode": 1, "errorMessage": "手机号不能为空", "data": null}
```

只看状态码会以为一切正常，然后 `data` 是 null、静默退化成「没拿到余额」，
表现成「功能没生效」。判断成功一律看 `success`。

**② 它要的是 `telPhone`，不是 `telephone`。** 绝大多数 GET 接口只认 `telephone`，
这个偏偏要 `telPhone`，少传就报上面那个「手机号不能为空」。
如果用拦截器统一补参数，**两个都要补**。

### 未签约时

`signStatus == 0`（没签约校园卡免密支付）时服务端不给 `amount`，
只能回退到本地估算：在钱包页手动输入初始余额，之后根据账单消费记录自动扣减
（仅扣除填写时间之后的新账单）。

> 余额优先级实际有三档：一卡通真实余额 → 趣智校园钱包（`/account/wallet` 的 `money`）→ 本地估算。
> 标题要按来源分别显示「一卡通余额」/「趣智校园余额」，别混成一个词。

### 附：易校园那条路（历史结论，**已作废**）

> 一卡通余额原先被认为必须直接调易校园（包名 `cn.com.yunma.school.app`，

## 九、开发建议

### 技术栈

| 组件 | 库 |
|---|---|
| HTTP | Retrofit + OkHttp（返回 `ResponseBody` 手动解析，绕开 R8 泛型擦除） |
| JSON | Gson（`JsonParser.parseString`，别用已弃用的 `JsonParser().parse()`） |
| MQTT | Eclipse Paho Android |
| BLE | Android BluetoothLeScanner + BluetoothGatt（自定义分片写入） |
| UI | Jetpack Compose + Material3 |
| 扫码 | CameraX + ML Kit |
| 存储 | EncryptedSharedPreferences |
| 构建 | Kotlin + JDK 21；`minSdk 26` / `targetSdk 36`；**仅 arm64-v8a** |

构建变体两个：`store`（发布，无预置凭证）与 `dev`（包名加 `.dev` 后缀、`versionName` 加
`-dev`、可从 `local.properties` 注入 `QZXY_PREFILL_*` 预置登录态）。
单元测试命令是 `:app:testDevDebugUnitTest`（任务名带 flavor，`testDebugUnitTest` 不存在）。

### 关键坑点

1. **`query/rateOrder/using` 返回 `errorCode=307` 时才是使用中**，不要只判断 `success=true`
2. **按量单的 `orderNo` 在 `downRateResult` 响应里**（v3.0.3 才修正的认识），
   等 MQTT 会绕远路，且在「开完水马上停」时丢过订单号
3. **套餐单的 `orderNo` 不在 HTTP 响应里**，见 6.4
4. **挤号检测**：服务器返回含「登录/token/失效/过期」的消息时清 token 跳回登录页。
   本项目另加 25 秒心跳轮询主动发现（被动检测用户挂着不动就永远发现不了）
5. **开阀需确认**：`downRate` 后轮询 `/order/tcpDevice/query/downRateResult` 确认开阀成功，
   避免设备离线时误以为已开
6. **热水器自动关停**：解析 `autoDisConTime`（秒）做倒计时；后台服务每 15 秒查一次
   `query/rateOrder/using` 兜底检测是否已被外部关闭（快关停时精确睡到那一刻）
7. **计时器持久化**：存 Unix 时间戳（加密），App 重启后算差值恢复，不需要后台常驻
8. **金额换算只用一处**：服务端金额有「厘整数」「元字符串」两种口径，差 1000 倍。
   统一走 `MoneyFormat.milliToYuan()` / `format()`
9. **失败一律看 `success`**，但**占用类判断要看 `errorCode`**（307），两者缺一不可
10. **蓝牙表不要接热水器的订单轮询**：它的阀是手机开的，`queryUsing` 不是有效信号源

### 不同学校的适配

**首先要澄清一个常见误解：projectId 不需要手动配置，更不需要抓包。**
每所学校的 projectId 确实不同，但它是**服务器在登录时下发的**——`/user/login` 的响应里带着
`userAccount.projectId`，客户端保存后自动沿用到后续所有请求。项目代码里没有硬编码任何学校的
projectId，所以换学校不需要改代码（多项目账号见第四节，仍是从 `/user/project/list` 读）。

真正可能需要适配的只有这几处：

| 位置 | 当前值 | 不改的影响 |
|---|---|---|
| BLE 设备名过滤 | `KLCXKJ-Water` | 扫不到附近设备；扫码绑定仍可用 |
| MQTT broker | `tcp://47.107.37.60:1883` | 收不到实时消费推送（开关阀不受影响，HTTP 轮询兜底）；套餐单拿不到 `orderNo` 会退到 byMac |
| `Config-Keys` 请求头 | 见第二节 | 结算类接口报 `226 加密校验失败` |
| 设备类型/计费判据 | `bigTypeId` / `smallTypeId` 数字 | 误判会把不该走套餐的设备接进套餐通道（= 扣错钱） |

各校接入的设备类型可能不同（热水器 / 洗手台 / 直饮水机 / 洗衣机 / 吹风机），
类型识别与设备名简化规则在 `model/DeviceModels.kt`，遇到识别不准的设备可在那里补。

## 十、已知限制

| 限制 | 说明 |
|---|---|
| 实时扣费 | 服务器不提供中间消费数据，只能等订单结束的推送 |
| **套餐无停止/退款** | 服务端根本没有这个接口，所以界面也不该给按钮 |
| **`lastOrder/byMac` 有时间窗口** | 实测 1 小时前的单查得到、19 天前返回 `null`；乱填 MAC 也是同样的 `null`，不能当「设备空闲」判据 |
| **MQTT broker 地址不一致** | 代码硬编码 `tcp://47.107.37.60:1883`（洗衣机 10-05 抓包就是这个），但**吹风机 10-24 抓包实测是 `39.108.147.136:1883`**。连不上时一条推送都收不到 → 套餐单 `orderNo` 退到 `lastOrder/byMac` 兜底（慢几秒，功能不挂）。可能按学校/项目分片，也可能旧地址已下线 |
| **服务端不下发 `isBle`** | 实测某校 `/device/info/mac` 里该字段出现 0 次。蓝牙表只能靠「云端开阀吃 306 + 用户确认」识别 |
| **`/project/module/list` 不是所有板块都能调** | 用 4000 调报「没有项目权限」，不能靠它判断某个板块有哪些业务 |
| **认证参数是全局共享的** | 跨板块借参数只读时必须串行，否则并发请求会带错 `projectId`/`accountId` |
| **`bill/detail` 兜底未接入** | 它是无时间窗口的 `orderNo` 来源，但手机与服务端时钟差几十秒就查不到，需要 ±2 分钟试探 |
| **饮水机未实机验证** | 识别与 UI 都已实现，但控制流程没有实机跑过；计费模型已确认是「按量」（账单 `preDeduct != consumeMoney`） |
| **洗衣机真实下单未实测** | 只完整跑过吹风机那一条链路（含扣款） |
| **自己的单占用态未采样** | `washer/status` 的 `isOwner=true` 长什么样没抓到 |
| **ColorOS 流体云胶囊需要用户手动开权限** | 设置 → 通知与状态栏 → 流体云 → 本 App。**代码无法代劳**，没开就完全没有胶囊。另一条依赖是通知带 `requestPromotedOngoing`；胶囊文本必须由 App 提供（ColorOS 16 不实现「按 `when` 自动渲染」） |
| **仅 arm64-v8a** | 纯 32 位老机型和 x86 模拟器装不上 |
| **一卡通余额需已签约** | 走 `/settlement/campus/userInfo` 能直接拿到真实余额；**没签约免密支付**时服务端不给 `amount`，只能回退本地估算 |
| **各校部署差异** | projectId 会自动下发，通常无需改动；但 BLE 广播名 / MQTT 地址 / `Config-Keys` / 接入设备类型可能不同 |
| **挤号检测有延迟** | 靠 25 秒心跳轮询发现，不是实时 |
| **MQTT 明文无认证** | `tcp://`，同一 broker 上的任何人可订阅 `app_downRate_{手机号}`，不要在里面放敏感数据 |
